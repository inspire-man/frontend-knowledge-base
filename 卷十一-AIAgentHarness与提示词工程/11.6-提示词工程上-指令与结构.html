11.6 提示词工程(上):指令与结构 ​

卷:卷十一 · AI Agent Harness 与提示词工程 阅读时间:25min

引言:提示词 = 把"意图 + 约束"写进上下文的输入 ​

提示词工程不是"会写套话",而是用结构化方式,把任务、约束、格式讲清楚,引导模型输出想要的东西。上半部分讲"指令与结构",下半部分(11.7)讲"推理增强"。

一、好提示词的结构骨架 ​

① 角色(Role):你是谁,以什么视角
② 任务(Task):做什么,目标是什么
③ 上下文(Context):必要背景、约束
④ 约束(Constraints):边界、不许做什么
⑤ 输出格式(Output):结果长什么样(JSON/表格/步骤)

背景:Vue3 项目,目标移动端(上下文)。
要求:只指出问题不改代码;每条给"问题-原因-建议"(约束)。
输出:Markdown 表格,列【问题|原因|建议】(输出格式)。

二、指令遵循四要点 ​

要点说明
具体越具体越可控
给边界明确"不要做什么"
给格式指定输出结构
给示例few-shot 示范

约束(负面)往往比指令(正面)更能压幻觉:"不要编造 API、不知道就说不知道"这类负面指令很关键(呼应 11.1)。

三、输出格式约束:让结果"可解析" ​

Agent 场景里模型输出常被程序解析,所以要:

  1. 指定格式(JSON/XML/Markdown)
  2. 配低温(降随机,提格式稳定)
  3. 用工具 JSON Schema 硬约束(最稳)
markdown
只输出一个 JSON,不要其他文字:{"result": "通过/不通过", "reason": "一句话"}
1

原则:凡下游要解析的输出,都要锁格式——口头"大概输出个 JSON"必出错。

四、few-shot:用示例"编程"行为 ​

"太棒了" → 正面
"真烂" → 负面
"还行吧" →           ← 模型按示例补出"中性/正面"

五、小结 ​

结构:角色+任务+上下文+约束+输出格式
遵循:具体/边界(负面压幻觉)/格式/示例
输出:JSON 化 + 低温 + 结构化输出;要解析必锁格式
few-shot:示例即"上下文里的编程"

六、思考题 ​

Q1:为什么"负面约束"("不要编造""不知道就说不知道")很重要?

模型是"概率补全"而非查库,默认倾向给看似合理的答案(幻觉)。正面指令告诉它"做什么",负面约束告诉它"做不出来的边界在哪",显著抑制没把握时乱编。

Q2:让模型稳定输出 JSON,有哪些手段?

① 提示里明确 JSON 结构与字段;② 调低 temperature;③ 用结构化输出/函数调用的 schema 硬约束(最稳);④ few-shot 给 JSON 示例;⑤ 解析失败把错误喂回重试。

Q3:好提示词的结构骨架是什么?

角色 + 任务 + 上下文 + 约束 + 输出格式五要素。五项分离、各说各的,比一段糊话更可控。

Q4:few-shot 的三个技巧?

① 示例覆盖边界情况(正/负/中性都来一个);② 与目标格式严格一致;③ 重质量不重数量(关键示例 > 一堆平庸示例)。

Q5:为什么"输出格式要锁"?怎么锁?

凡下游要程序解析的输出,口头"大概输出 JSON"必出错。锁法:① 提示里明确结构字段;② 降 temperature;③ 结构化输出硬约束;④ 解析失败把错误喂回重试。

Q6:为什么"约束(负面)"往往比"指令(正面)"更能压幻觉?

正面指令告诉它"做什么",负面约束告诉它"做不出来的边界在哪儿"。模型默认倾向给看似合理的答案,负面约束直接抑制"没把握时乱编"。
