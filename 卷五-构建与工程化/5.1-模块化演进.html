5.1 模块化演进(IIFE → CJS → AMD → ESM) ​

引言:模块化是"工程化"的起点 ​

没有模块化,所有 JS 挤全局作用域、变量互污染、依赖靠手动排 <script> 顺序。模块化演进史 = "如何组织代码、隔离作用域、描述依赖"的解题史。深挖要懂 ESM 活引用 与 循环依赖。

五个缩写先记全称:

  • IIFE = Immediately Invoked Function Expression,立即执行函数表达式
  • CJS / CommonJS = 服务端模块规范(require/module.exports)
  • AMD = Asynchronous Module Definition,异步模块定义(浏览器)
  • UMD = Universal Module Definition,通用模块定义(兼容兜底)
  • ESM / ES Module = ECMAScript 官方模块标准(静态、可树摇)

一、模块化解决了三个痛点 ​

早期 JS 全靠 <script> 标签顺序加载,于是:

  1. 全局污染:所有变量挂在 window,命名冲突
  2. 依赖不清晰:靠"谁先定义谁后用"的人肉约定,顺序错了就崩
  3. 无法复用:代码耦合成一坨,难以拆解
html
<script src="a.js"></script>  <!-- 定义 var data -->
<script src="b.js"></script>  <!-- 依赖 a.js 的 data,但没声明 -->
<!-- b.js 改了 data,污染了全局,谁都说不清 -->

二、IIFE:函数作用域隔离 ​

用立即执行函数创建独立作用域,配合闭包返回接口(也即模块模式):

js
const myModule = (function () {
  const privateVar = "私有变量";          // 函数作用域内,外部拿不到
  function privateFn() { return privateVar; }
  return {
    publicMethod() { return privateFn(); },  // 只暴露需要的
  };
})();

myModule.publicMethod();   // "私有变量"
myModule.privateVar;       // undefined —— 隔离成功

四、AMD:浏览器异步 ​

浏览器里加载模块要异步(先声明依赖、下载完再执行),AMD + RequireJS 应运而生:

js
// 定义模块:先声明依赖 jquery/lodash,下载完成后回调
define(["jquery", "lodash"], function ($, _) {
  function init() { /* 用 $ 和 _ */ }
  return { init };
});

// 使用模块(RequireJS)
require(["moduleA"], function (A) {
  A.init();
});

五、UMD:通用兜底(兼容三平台) ​

库作者想"一份代码同时兼容 AMD + CJS + 全局挂载",于是有 UMD 模板:

js
(function (root, factory) {
  if (typeof define === "function" && define.amd) {
    define([], factory);                       // 1. AMD 环境
  } else if (typeof module === "object" && module.exports) {
    module.exports = factory();                // 2. CommonJS 环境
  } else {
    root.myLib = factory();                    // 3. 浏览器全局(window.myLib)
  }
})(typeof self !== "undefined" ? self : this, function () {
  return { hello: () => "hi" };
});

六、ESM:官方标准(静态、可树摇) ​

活引用 vs 值拷贝 ​

js
// CJS:导出的是"值快照"
// counter.js
let count = 0;
module.exports = { count, inc: () => count++ };
// main.js
const { count, inc } = require("./counter.js");
inc();
console.log(count);   // 0 ← 拷贝,不随 inc 变

// ESM:导出的是"活引用"
// counter.js
export let count = 0;
export const inc = () => count++;
// main.js
import { count, inc } from "./counter.js";
inc();
console.log(count);   // 1 ← 活引用,读到最新值

为什么 ESM 要"活引用"? 静态结构 + 活引用,让打包器能在编译期精确分析"谁用了谁、值如何流转",从而树摇 + 预计算。这是 ESM 成为构建标准的原因。

ESM 循环依赖:模块按图先执行,b 引 a 时 a 还没执行到 export → 拿到 undefined(或 TDZ 报错)。 CJS 循环依赖:require 返回"执行到一半"的 exports(部分完成对象,见 9.1)。 工程上尽量打破循环依赖:抽公共模块、依赖注入、事件解耦。

十、小结 ​

痛点:全局污染 / 依赖不清晰 / 无法复用
演进:IIFE(隔离)→ CJS(同步服务端)→ AMD(异步浏览器)→ UMD(通用兜底)→ ESM(静态标准)
核心:CJS 值拷贝 / ESM 活引用;ESM 静态可树摇
陷阱:循环依赖(ESM 拿 undefined/TDZ,CJS 拿半成品)→ 抽公共模块打破

十一、面试题 ​

Q1:为什么 ESM 能 tree-shaking,而 CommonJS 很难?

ESM 的 import/export 静态(编译期确定),打包器能分析"谁没用"安全删;CJS 的 require 运行时动态(可写进 if/循环/变量),无法静态确定,难无损摇树。

Q2:require 和 import 能混用吗?

能在打包器下互操作,但有坑:ESM import CJS 时 module.exports 变 default;CJS require ESM 要异步 import()。建议统一用 ESM。

Q3:什么是"活引用(live binding)"?举一个差异例子?

ESM 导出的是变量本身的可变绑定,导入方看到最新值;CJS 导出的是值的快照拷贝。例:计数器 count++ 后,ESM 里 count 是 1,CJS 里仍是 0。

Q4:ESM 循环依赖为什么拿到 undefined?

ESM 按模块图先执行,a 引 b、b 又引 a 时,若 a 还没执行到 export 就被 b 引用,拿到的是未初始化的绑定(undefined/TDZ)。

Q5:为什么浏览器原生支持 ESM 了,工程上还要打包?

① 兼容性(老浏览器转译);② 请求数(一个模块一个请求,打包成一个省请求);③ 能力扩展(TS/JSX、CSS、图片、分包优化)。

Q6:IIFE 解决什么问题?它的局限?

IIFE((function(){})())用函数作用域隔离变量,避免全局污染。局限:只是"隔离"不是"模块"——没有依赖声明,依赖仍靠全局变量传递,难管理复杂依赖。

Q7:UMD 是什么?解决什么问题?

通用模块定义——一份代码运行时探测环境,同时兼容 AMD / CommonJS / 浏览器全局三种加载方式。用于库的广泛分发;现代多由打包工具自动生成,不必手写。

Q8:AMD 和 CommonJS 最根本的区别是什么?

加载时机与目标环境:CJS 是同步加载(服务端本地磁盘,require 即得);AMD 是异步加载(浏览器需先下载依赖再执行,define 依赖前置)。本质是"服务端 vs 浏览器"的网络差异。
