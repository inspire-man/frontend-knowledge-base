5.2 Babel / SWC 转译原理 ​

卷:卷五 · 构建与工程化 阅读时间:20min

引言:为什么需要"转译" ​

浏览器能跑的 JS 有限:新语法、超集语法(JSX/TS)不能直接跑。转译器把它们变成兼容代码。这条路走过 Babel → SWC/esbuild 两代。深挖要懂 AST 工作流 与 语法转译 vs polyfill 的分野。

一、转译器干三件事 ​

  1. 语法转换:新语法 → 旧语法(?. → 判断)
  2. polyfill:补缺失 API(Promise、includes)
  3. 能力扩展:JSX/TS → JS
js
const f = (a = 1) => a ** 2;
// ↓
var f = function (a) { return Math.pow(a === undefined ? 1 : a, 2); };

二、Babel 工作流(一图) ​

  • Parser:源码 → AST(@babel/parser)
  • Transform:插件遍历/改 AST(核心,@babel/traverse)
  • Generator:AST → 代码(@babel/generator)

preset vs plugin:

json
{
  "presets": [["@babel/preset-env", { "targets": "> 1%, last 2 versions" }]],
  "plugins": ["@babel/plugin-transform-arrow-functions"]
}

preset = 一组 plugin 的集合。preset-env 根据 targets 按需引入转换,避免过度编译。

三、语法转译 vs polyfill(底层分野) ​

语法转译polyfill
改什么语法结构运行时 API
例子箭头函数→functionPromise/includes
手段AST 变换注入实现代码
js
// polyfill:补 API(core-js)
import "core-js/stable";
// 或 preset-env 配 useBuiltIns:'usage' 按用法自动引入

关键认知:语法能"改写",但 API(Promise 等)是"环境缺什么补什么",两者解决不同层面的兼容。现代推荐 preset-env + core-js 的 usage 模式,只引入实际用到的 polyfill。

四、SWC / esbuild:用更快语言重写 ​

BabelSWCesbuild
语言JSRustGo
速度慢(基准)快极快
生态最强中少

现状:Vite 用 esbuild 做依赖预构建,SWC 被 Next.js 采用;需深度自定义插件时 Babel 生态不可替代。三者常共存。

为什么 esbuild 快那么多? 用 Go 编译到原生机器码、内部并行、复用 AST、少做抽象;而 Babel 是 JS 实现,跑在 JS 引擎上、插件模型层数多。

五、小结 ​

转译 = 语法转换 + polyfill + 能力扩展
Babel:parse→transform(plugin/preset)→generate;preset-env 按 target 转
语法转译(改结构)vs polyfill(补 API);core-js + useBuiltIns:usage
演进:Babel(JS 全功能)→ SWC(Rust)/esbuild(Go,快 10~100 倍)

六、面试题 ​

Q1:preset 和 plugin 的区别?

plugin 是单个转换能力(转箭头函数);preset 是一组 plugin 的预设(preset-env/preset-react)。执行顺序:plugin 先于 preset。

Q2:语法转译和 polyfill 的区别?

语法转译改语法结构(箭头→function);polyfill 补运行时 API(Promise/includes)。两者解决不同层面的兼容。

Q3:为什么 esbuild 比 Babel 快那么多?

esbuild 用 Go 编译到原生机器码、内部并行、复用 AST;Babel 是 JS 实现,跑在 JS 引擎、插件抽象层多。这是"编译执行 vs 解释执行"的性能差距。

Q4:useBuiltIns: 'usage' 相比全量引入 polyfill 有什么好处?

全量引入所有 polyfill 体积大;usage 会分析代码实际用到的 API,只引入对应的 polyfill,体积最小。

Q5:什么场景还需要 Babel 而不是只用 esbuild/SWC?

需要深度自定义的 Babel 插件生态(如复杂代码生成、实验语法、特定 ast 变换)时,Babel 生态最全、最可扩展;esbuild/SWC 插件能力相对受限,适合"纯转译提速"。

Q6:Babel 的 transform 阶段到底在做什么?

在 AST 上运行插件:遍历节点(traverse),按规则增删改 AST 节点(如把箭头函数节点改成 function 节点),输出新 AST。这是转译的核心——"改的是树,不是文本"。
