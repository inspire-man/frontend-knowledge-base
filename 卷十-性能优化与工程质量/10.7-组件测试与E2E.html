10.7 组件测试与 E2E(Testing Library / Playwright) ​

引言:按"用户"而非"实现"测 ​

深挖要懂 Testing Library 的查询优先级 与 Playwright 的自动等待。

一、组件测试:按用户视角 ​

jsx
render(Counter);
fireEvent.click(screen.getByRole("button"));
expect(screen.getByText("1")).toBeTruthy();   // 断言"屏幕上显示1",而非内部 state
1
2
3

查询优先级(从高到低):

getByRole > getByLabelText > getByText > getByTestId(兜底)
1

为什么 role 优先(底层)? 可访问性好的组件天然有 role,按 role 测 = 顺便测了 a11y;testId 是"看不到"的实现细节,应最后才用。这就是"按用户而非实现测"的落地。

二、E2E:Playwright ​

js
import { test, expect } from "@playwright/test";
test("用户能登录", async ({ page }) => {
  await page.goto("/login");
  await page.fill('[name="email"]', "a@b.com");
  await page.click("button[type=submit]");
  await expect(page.getByText("欢迎")).toBeVisible();
});

  • 多浏览器、自动等待(元素就绪再操作)、录制、视觉回归、并行

为什么 Playwright 的自动等待重要(底层)? 传统 E2E 要手动 sleep 等元素/网络;Playwright 的 expect/操作自动重试直到条件满足,大幅减少"flaky(偶发失败)"。

三、选型 ​

层工具数量
单元Vitest多
组件Testing Library中
E2EPlaywright少

四、小结 ​

组件测试:按用户视角(role/text),testId 兜底
E2E:Playwright 多浏览器、自动等待、视觉回归
比例:单元多 > 组件中 > E2E 少

五、面试题 ​

Q1:组件测试为什么按 role 查询而非 testId?

按 role/text 贴近用户感知、天然覆盖 a11y;testId 是内部实现、变化频繁、测不到真实体验。能 role 就别 testId。

Q2:Playwright 相比 Cypress 的优势?

支持更多浏览器(含 WebKit)、自动等待更强、原生并行 + 录制 + 视觉回归,对现代 Web(多标签/网络拦截)支持更好。

Q3:什么是"flaky test"?如何减少?

偶发失败的测试(依赖时序/竞态)。减少:用自动等待(Playwright 的 expect 重试)、避免硬编码 sleep、测试隔离、稳定选择器。

Q4:E2E 测试为什么"少而慢"?适合测什么?

E2E 跑真实浏览器 + 完整流程,慢且脆、维护贵。适合测核心用户旅程(登录/下单),不适合测每个分支。

Q5:视觉回归测试是什么?

用 Playwright 的 toHaveScreenshot 对比页面像素快照,捕获"意外视觉变化"。适合 UI 库/组件库防样式回归。

Q6:组件测试和单元测试的边界?

单元测纯逻辑(函数、工具);组件测渲染 + 交互(按用户视角断言 DOM)。组件测试更接近"用户看到什么",单元测试更接近"函数返回什么"。
