# 10.8 代码规范与工程质量

## 引言:三道关卡:格式、质量、提交

深挖要懂 **Prettier vs ESLint 的分工** 与 lint-staged 的增量价值。

---

## 一、三关卡

```mermaid
flowchart LR
    A[写代码] --> B[Prettier 格式化]
    B --> C[ESLint 质量检查]
    C --> D[husky + lint-staged 提交拦截]
    D --> E[CI: typecheck + test + build]
```

---

## 二、Prettier vs ESLint(分工)

| | Prettier | ESLint |
|---|----------|--------|
| 管什么 | **格式**(缩进/引号/换行) | **质量**(未用变量/错误模式) |
| 自动修 | `--write` 全部 | `--fix` 部分 |

> 分工:**Prettier 管"好看",ESLint 管"别错"**。别让 ESLint 干格式的活。

**为什么两者会冲突?怎么协调(底层):** 规则重叠(缩进/引号)。协调:用 `eslint-config-prettier` **关掉 ESLint 里与格式冲突的规则**,格式全交 Prettier,ESLint 只负责逻辑质量。

---

## 三、Git Hooks:husky + lint-staged

```json
{ "lint-staged": { "*.{js,ts,vue}": ["eslint --fix", "prettier --write"] } }
```

```bash
npx husky add .husky/pre-commit "npx lint-staged"
```

**lint-staged 的价值(底层):** 只对**已暂存文件**跑检查——快(增量),且保证"进仓库的代码是干净的"。husky 挂 git 生命周期,提交即触发。

---

## 四、CI 质量关卡

```yaml
- run: pnpm lint && pnpm typecheck && pnpm test && pnpm build
```

> 把质量写进 CI(呼应 [5.8](/卷五-构建与工程化/5.8-Monorepo与CICD)):任何一步红就阻断合并。**问题越早拦住越便宜**(编辑器 > 提交 > CI > 线上)。

---

## 五、小结

```
Prettier 格式 / ESLint 质量 / lint-staged+husky 提交前拦截 / CI 四关
协调:eslint-config-prettier 关冲突规则
```

## 六、面试题

**Q1:Prettier 和 ESLint 会冲突吗?怎么协调?**

会(缩进/引号重叠)。协调:用 `eslint-config-prettier` **关掉 ESLint 与格式冲突的规则**,格式交 Prettier,ESLint 只管逻辑。

**Q2:husky + lint-staged 是做什么的?价值?**

husky 把脚本挂 **git hooks**(pre-commit),lint-staged 只对**暂存文件**跑检查。提交前自动拦截格式/错误,且只跑增量、快。

**Q3:为什么"问题越早拦住越便宜"?**

修复成本随"被发现的时间"指数上升:编辑器(秒)→ 提交(分)→ CI(小时)→ 线上(事故)。所以前置检查(husky/CI)省大量成本。

**Q4:ESLint 的 `--fix` 能修所有问题吗?**

不能。只修**可自动修复**的规则(格式、语法糖);逻辑性/安全性的规则需人工改。所以 "--fix 后仍需人工 review 未修复项"。

**Q5:typecheck 为什么要单独在 CI 里跑?**

转译工具(esbuild/SWC)只擦类型不查类型(8.4);单独 `tsc --noEmit` 保证类型安全不被"转译通过"掩盖。

**Q6:代码规范的核心目标是什么?**

**一致性 + 可维护性 + 防错**:统一风格降低 review 噪音、自动化拦截低级错误、让团队专注逻辑而非格式。
