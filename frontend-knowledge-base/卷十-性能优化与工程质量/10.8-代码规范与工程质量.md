# 10.8 代码规范与工程质量

> 卷:卷十 · 性能优化与工程质量
> 难度:⭐ 基础 | 阅读时间:15min

---

## 一、三道关卡:格式、质量、提交

```mermaid
flowchart LR
    A[写代码] --> B[格式化:Prettier]
    B --> C[质量检查:ESLint]
    C --> D[提交前:lint-staged + husky]
    D --> E[CI:typecheck + test + build]
```

## 二、Prettier(格式)vs ESLint(质量)

| | Prettier | ESLint |
|---|----------|--------|
| 管什么 | **格式**(缩进/引号/换行) | **质量**(未用变量/错误模式/规范) |
| 自动修 | `--write` 全部 | `--fix` 部分 |

> 分工:**Prettier 管"好看",ESLint 管"别错"**。二者配合,别让 ESLint 去干格式的活。

## 三、Git Hooks:husky + lint-staged

提交前自动跑,把问题挡在仓库外:

```json
// package.json
{ "lint-staged": { "*.{js,ts,vue}": ["eslint --fix", "prettier --write"] } }
```

```bash
npx husky add .husky/pre-commit "npx lint-staged"
```

> **lint-staged 只跑"已暂存"的文件**,快;husky 挂到 git 生命周期,提交即触发。

## 四、CI 里的质量关卡

```yaml
- run: pnpm lint        # 规范
- run: pnpm typecheck   # 类型
- run: pnpm test        # 单测
- run: pnpm build       # 构建
```

> 把"质量"写进 CI(呼应 5.8):任何一步红了就阻断合并。

## 小结

```
Prettier 格式 / ESLint 质量 / lint-staged+husky 提交前拦截 / CI 四关
目标:问题越早拦住越便宜(编辑器 > 提交 > CI > 线上)
```

## 面试题

**Q1:Prettier 和 ESLint 会冲突吗?怎么协调?**

会(如缩进、引号规则重叠)。协调:用 `eslint-config-prettier` **关掉 ESLint 里与格式冲突的规则**,格式全交给 Prettier,ESLint 只负责逻辑质量。

**Q2:husky + lint-staged 是做什么的,为什么有价值?**

husky 把脚本挂到 **git hooks**(如 pre-commit),lint-staged 只对**已暂存文件**跑检查。价值:在**提交前自动拦截**格式/错误,保证进入仓库的代码是干净的,且只跑增量、快。
