# 10.8 代码规范与工程质量

## 引言:三道关卡:格式、质量、提交

深挖要懂 **Prettier vs ESLint 的分工** 与 lint-staged 的增量价值。这一章把前端工程化的"质量工具链"讲全,并给一套可直接抄的配置。

---

## 一、三关卡

```mermaid
flowchart LR
    A[写代码] --> B[Prettier 格式化]
    B --> C[ESLint 质量检查]
    C --> D[husky + lint-staged 提交拦截]
    D --> E[CI: typecheck + test + build]
```

## 二、Prettier vs ESLint(分工)

| | Prettier | ESLint |
|---|----------|--------|
| 管什么 | **格式**(缩进/引号/换行) | **质量**(未用变量/错误模式) |
| 自动修 | `--write` 全部 | `--fix` 部分 |

> 分工:**Prettier 管"好看",ESLint 管"别错"**。

### Prettier 配置

```json
// .prettierrc
{
  "semi": true,
  "singleQuote": true,
  "printWidth": 100,
  "tabWidth": 2,
  "trailingComma": "all"
}
```

### ESLint 配置

```js
// eslint.config.js(flat config)
export default [
  { rules: { "no-unused-vars": "error", "no-console": "warn" } },
];
```

| 规则类型 | 示例 |
|---------|------|
| 逻辑错误 | `no-undef`(未定义变量)、`no-dupe-keys` |
| 最佳实践 | `eqeqeq`(用 ===)、`no-var` |
| 风格(交给 Prettier) | `quotes`、`indent`(应关掉) |

**为什么两者冲突?怎么协调?** 规则重叠(缩进/引号)。用 **`eslint-config-prettier` 关掉 ESLint 里与格式冲突的规则**,格式全交 Prettier,ESLint 只负责逻辑质量。

## 三、EditorConfig(编辑器层统一)

```ini
# .editorconfig
root = true
[*]
indent_style = space
indent_size = 2
charset = utf-8
end_of_line = lf
insert_final_newline = true
```

> EditorConfig 在**编辑器层面**统一缩进/换行,比 Prettier 更底层、更早生效——是"问题越早拦住越便宜"的第一环。

## 四、Git Hooks:husky + lint-staged + commitlint

```json
// package.json
{
  "lint-staged": { "*.{js,ts,vue}": ["eslint --fix", "prettier --write"] }
}
```

```bash
npx husky add .husky/pre-commit "npx lint-staged"
npx husky add .husky/commit-msg "npx commitlint --edit $1"
```

**commitlint(提交信息规范):**

```js
// commitlint.config.js —— Conventional Commits
export default { extends: ["@commitlint/config-conventional"] };
// 提交信息格式:feat: 新功能 / fix: 修复 / docs: 文档 / chore: 杂项
```

**lint-staged 的价值:** 只对**已暂存文件**跑检查——快(增量),且保证"进仓库的代码是干净的"。husky 挂 git 生命周期,提交即触发。

## 五、CI 质量关卡(完整)

```yaml
# .github/workflows/ci.yml
jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint          # 规范
      - run: pnpm typecheck     # 类型
      - run: pnpm test          # 单测
      - run: pnpm build         # 构建
```

> 任何一步红就阻断合并。**问题越早拦住越便宜**:编辑器(秒)→ 提交(分)→ CI(小时)→ 线上(事故)。

## 六、小结

```
工具链:EditorConfig(缩进)→ Prettier(格式)→ ESLint(质量)→ lint-staged+husky(提交拦截)→ CI(四关)
协调:eslint-config-prettier 关冲突规则;commitlint 规范提交信息
```

## 七、面试题

**Q1:Prettier 和 ESLint 会冲突吗?怎么协调?**

会(缩进/引号重叠)。协调:用 `eslint-config-prettier` **关掉 ESLint 与格式冲突的规则**,格式交 Prettier,ESLint 只管逻辑。

**Q2:husky + lint-staged 是做什么的?价值?**

husky 把脚本挂 **git hooks**(pre-commit),lint-staged 只对**暂存文件**跑检查。提交前自动拦截格式/错误,且只跑增量、快。

**Q3:为什么"问题越早拦住越便宜"?**

修复成本随"被发现的时间"指数上升:编辑器(秒)→ 提交(分)→ CI(小时)→ 线上(事故)。所以前置检查(husky/CI)省大量成本。

**Q4:ESLint 的 `--fix` 能修所有问题吗?**

不能。只修**可自动修复**的规则(格式、语法糖);逻辑性/安全性的规则需人工改。所以 "--fix 后仍需人工 review 未修复项"。

**Q5:typecheck 为什么要单独在 CI 里跑?**

转译工具(esbuild/SWC)只擦类型不查类型(8.4);单独 `tsc --noEmit` 保证类型安全不被"转译通过"掩盖。

**Q6:代码规范的核心目标是什么?**

**一致性 + 可维护性 + 防错**:统一风格降低 review 噪音、自动化拦截低级错误、让团队专注逻辑而非格式。

**Q7:EditorConfig 和 Prettier 有什么区别?**

EditorConfig 在**编辑器层**统一缩进/换行等基础(所有语言通用、最早生效);Prettier 是**代码格式化器**,按语言规则重排代码(自动加/删空格、换行)。两者互补:EditorConfig 保证编辑器行为一致,Prettier 保证产物格式一致。

**Q8:commitlint 的 Conventional Commits 规范有什么用?**

规范提交信息格式(`feat: xxx` / `fix: xxx`),让**提交历史可读、可自动生成 CHANGELOG、可做版本发布语义推断**。核心是"**人 + 工具都能读懂提交意图**"。
