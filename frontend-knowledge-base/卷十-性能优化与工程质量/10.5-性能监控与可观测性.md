# 10.5 性能监控与可观测性

## 引言:上线后才知道"用户到底卡不卡"

本地跑得快不代表用户体感好。**RUM(真实用户监控)** 收集的是真实用户设备上的数据,才能发现"环境差异导致的问题"。这一章讲清采集、上报、追踪三件事。

---

## 一、Performance API(浏览器内置的测量能力)

### 1. 拿页面加载时间点

```js
const t = performance.getEntriesByType("navigation")[0];
t.domContentLoadedEventEnd;   // DCL
t.loadEventEnd;               // load
t.transferSize;               // 传输体积
```

### 2. 自定义耗时打点

```js
performance.mark("start");
// ...业务逻辑...
performance.mark("end");
const d = performance.measure("task", "start", "end").duration;
console.log(d);   // 毫秒
```

### 3. PerformanceObserver(异步监听,推荐)

```js
const po = new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    console.log(e.name, e.startTime, e.duration);
  }
});
po.observe({ entryTypes: ["largest-contentful-paint", "longtask"], buffered: true });
```

**常用 entryTypes:**

| entryType | 监听的条目 |
|-----------|-----------|
| `largest-contentful-paint` | LCP |
| `longtask` | 长任务(>50ms) |
| `layout-shift` | 布局偏移(CLS) |
| `resource` | 资源加载 |
| `navigation` | 导航时间点 |
| `paint` | FCP/FP |
| `event` | 交互延迟(INP) |

**`PerformanceObserver` 的底层:** 它用**观察者模式**异步监听 `performance` 时间轴——注册 `observe` 后,浏览器在**性能条目产生时批量回调**(而非轮询),`PerformanceEntry` 自带 name/startTime/duration 等结构化数据。`buffered: true` 能回放"注册前已产生"的条目(如 LCP 发生在监听器挂载前也不丢)。

## 二、web-vitals 打点(生产采集)

```js
import { onLCP, onINP, onCLS } from "web-vitals";
onLCP((m) => report("LCP", m.value));
onINP((m) => report("INP", m.value));
onCLS((m) => report("CLS", m.value));

function report(metric, value) {
  navigator.sendBeacon("/analytics", JSON.stringify({ metric, value }));
}
```

**为什么用 `navigator.sendBeacon`?** 页面**卸载时**异步请求可能被取消,`sendBeacon` 保证"浏览器一定尽力把数据发出去"——适合最后关头的数据上报(如 CLS 往往在页面快关闭时才确定)。

## 三、上报机制(采集 → 采样 → 批量 → 上报)

```mermaid
flowchart LR
    A[采集] --> B[采样<br/>降量]
    B --> C[批量聚合<br/>降请求]
    C --> D[上报<br/>sendBeacon/fetch]
    D --> E[监控平台]
```

| 环节 | 手段 | 目的 |
|------|------|------|
| 采样 | 只报 X% 的数据 | 降成本、防刷 |
| 批量 | 攒一批一起发 | 降请求数 |
| 上报 | `sendBeacon`/`fetch` | 可靠送达 |
| 聚合 | 平台按分位(P50/P75/P95) | 看分布非平均值 |

> 关键:**看 P95 而非平均值**——平均值被极端值拉偏,分位数才反映"大多数用户"的真实体感。

## 四、错误监控(捕获 → 解析 → 定位)

### 1. 四种错误类型

```js
// ① 运行时错误(同步)
window.onerror = (msg, src, line, col) => report({ msg, src, line, col });

// ② Promise 未处理拒绝
window.addEventListener("unhandledrejection", (e) => report({ reason: e.reason }));

// ③ 资源加载错误(图片/脚本 404)
window.addEventListener("error", (e) => {
  if (e.target !== window) report({ type: "resource", src: e.target.src });
}, true);

// ④ 框架错误边界(React/Vue 捕获组件渲染异常)
```

## 五、可观测性三支柱

| 支柱 | 工具 | 关注 |
|------|------|------|
| 指标 Metrics | web-vitals + 平台 | LCP/INP/CLS/错误率 |
| 日志 Logs | 结构化日志 | 定位线上问题 |
| 链路 Tracing | Sentry/OpenTelemetry | 请求→报错链路 |
| 错误监控 | Sentry | 报错堆栈、影响面 |

> **指标看趋势、日志看现场、链路看归因、错误看影响**——四者互补,缺一个都定位不完整。

## 六、小结

```
RUM 真实用户监控 > 本地测试
API:Performance(时间点/打点)+ PerformanceObserver(异步监听)+ web-vitals(封装)
上报:采样→批量→sendBeacon;看 P95 而非平均
错误:4 种类型 + sourcemap 还原 + Sentry
三支柱:指标(logs)/日志(metrics)/链路(traces)/错误
```

## 七、面试题

**Q1:为什么不能只看 Lighthouse 跑分?**

Lighthouse 是**本地合成测试**,不代表真实用户(网络/设备/地域);需 **RUM** 采生产数据。Lighthouse 定位问题,RUM 验证真实体感。

**Q2:如何监控前端报错?**

`window.onerror`/`unhandledrejection`/资源 error 捕获 → 上报 Sentry(堆栈 + sourcemap 还原)→ 结合行为回放定位复现。

**Q3:什么是"可观测性"?三大支柱?**

可观测性 = 系统"能从外部数据推断内部状态"的能力。三支柱:**日志(logs)、指标(metrics)、链路(traces)**;前端再加**错误监控**。

**Q4:web-vitals 库解决什么?**

封装 CWV 指标(LCP/INP/CLS)的**采集与上报**,生产环境打点,替代手写 PerformanceObserver。

**Q5:sourcemap 在错误监控里起什么作用?**

线上代码是**压缩混淆**的,报错堆栈不可读;sourcemap 把堆栈**还原成源码位置**,才能定位到具体行。所以上报要带 sourcemap(注意保密)。

**Q6:为什么"指标、日志、链路"三者都要?**

指标看**趋势**、日志看**现场**、链路看**归因**。三者互补,单靠一个定位不了完整问题。

**Q7:`sendBeacon` 相比 `fetch` 上报,优势在哪?**

`sendBeacon` 在页面**卸载/跳转**时也能保证把数据发出去(浏览器尽力送达),而 `fetch` 异步请求在页面卸载时可能被取消。适合"页面生命最后关头"的数据上报(如 CLS)。代价:只能 POST、数据量小。

**Q8:上报性能数据,为什么看 P95 而不是平均值?**

平均值被少数**极端值**拉偏(一两个极慢用户会掩盖整体);**P95 分位数**反映"95% 的用户体验在多少以内",更能代表真实分布、更早暴露长尾恶化。
