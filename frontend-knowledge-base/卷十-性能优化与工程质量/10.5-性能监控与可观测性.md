## 一、Performance API

```js
const t = performance.getEntriesByType("navigation")[0];
t.domContentLoadedEventEnd;   // DCL
performance.mark("start"); /* ... */ performance.mark("end");
performance.measure("task", "start", "end").duration;
```

- **PerformanceObserver** 监听 LCP/CLS/INP/长任务等事件

**`PerformanceObserver` 的底层原理:**

它用**观察者模式**异步监听 `performance` 时间轴上的条目(entry):注册 `observe({ entryTypes: [...] })` 后,浏览器在**性能条目产生时批量回调**(而非轮询),拿到的 `PerformanceEntry` 自带 name/startTime/duration 等结构化数据。

```js
const po = new PerformanceObserver((list) => {
  for (const e of list.getEntries()) console.log(e.name, e.startTime);
});
po.observe({ entryTypes: ["largest-contentful-paint", "longtask"] });
```

> 关键:`observe` 支持 `buffered: true` 能回放"注册前已产生"的条目(如 LCP 发生在监听器挂载前也不丢)。

📎 官方:MDN《PerformanceObserver》/《PerformanceEntry》

## 三、可观测性三支柱(底层)

| 支柱 | 工具 | 关注 |
|------|------|------|
| 指标 Metrics | web-vitals + 平台 | LCP/INP/CLS/错误率 |
| 日志 Logs | 结构化日志 | 定位线上问题 |
| 链路 Tracing | Sentry/OpenTelemetry | 请求→报错链路 |
| 错误监控 | Sentry | 报错堆栈、影响面 |

> 一句话:**指标看趋势、日志看现场、链路看归因、错误看影响**。

**前端报错监控怎么捕获(底层):**

```js
window.onerror;              // 同步错误
window.addEventListener("unhandledrejection");  // Promise 未处理拒绝
// 上报 Sentry + sourcemap 还原堆栈
```

## 五、面试题

**Q1:为什么不能只看 Lighthouse 跑分?**

Lighthouse 是**本地合成测试**,不代表真实用户(网络/设备/地域);需 **RUM** 采生产数据。Lighthouse 定位问题,RUM 验证真实体感。

**Q2:如何监控前端报错?**

`window.onerror`/`unhandledrejection` 捕获 → 上报 Sentry(堆栈 + sourcemap 还原)→ 结合行为回放定位复现。

**Q3:什么是"可观测性"?三大支柱?**

可观测性 = 系统"能从外部数据推断内部状态"的能力。三支柱:**日志(logs)、指标(metrics)、链路(traces)**;前端再加**错误监控**。

**Q4:web-vitals 库解决什么?**

封装 CWV 指标(LCP/INP/CLS)的**采集与上报**,生产环境打点,替代手写 PerformanceObserver。

**Q5:sourcemap 在错误监控里起什么作用?**

线上代码是**压缩混淆**的,报错堆栈不可读;sourcemap 把堆栈**还原成源码位置**,才能定位到具体行。所以上报要带 sourcemap(注意保密)。

**Q6:为什么"指标、日志、链路"三者都要?**

指标看**趋势**(有没有变差)、日志看**现场**(发生了什么)、链路看**归因**(哪一步慢/错)。三者互补,单靠一个定位不了完整问题。
