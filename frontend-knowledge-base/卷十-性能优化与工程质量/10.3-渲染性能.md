# 10.3 渲染性能(减少重排 / 长任务 / 首屏)

## 引言:渲染性能 = 别让主线程被占死

与卷二(2.4/2.5)强关联,这里做"工程落地"汇总。核心三件事:**少重排、拆长任务、快首屏**。

---

## 一、减少重排/重绘(原理见 [2.4](/卷二-浏览器工作原理/2.4-重排与重绘))

### 1. 读写分离(避免强制同步布局)

```js
// ❌ 读读写写交替:每次读都强制立即重排
for (let i = 0; i < 100; i++) {
  el.style.width = i + "px";
  total += el.offsetWidth;   // 读 → 强制重排 100 次
}

// ✅ 先读后写:只重排一次
const w = el.offsetWidth;
for (let i = 0; i < 100; i++) {
  el.style.width = i + "px";
}
```

### 2. 离线 DOM(批量插入)

```js
// ✅ DocumentFragment:内存里组装,一次性插入,只重排一次
const frag = document.createDocumentFragment();
for (let i = 0; i < 1000; i++) {
  const li = document.createElement("li");
  li.textContent = i;
  frag.appendChild(li);
}
ul.appendChild(frag);   // 一次挂载
```

### 3. 隐藏后批量改

```js
el.style.display = "none";   // 脱离布局树
// ...大量修改样式...
el.style.display = "block";  // 重新进布局,只重排两次
```

### 4. 动画只动 transform/opacity

```js
// ❌ 改 left:帧帧重排
el.style.left = x + "px";
// ✅ 改 transform:只走合成
el.style.transform = `translateX(${x}px)`;
```

> 属性触发分级速查见 [2.4](/卷二-浏览器工作原理/2.4-重排与重绘):几何→reflow、颜色→repaint、transform/opacity→合成。

## 二、长任务拆分(INP 的关键)

**长任务(Long Task):** 单次任务 **> 50ms** 就会阻塞交互、抬高 INP。

### 1. 时间切片(setTimeout 让出)

```js
async function processChunks(items, chunkFn, size = 1000) {
  for (let i = 0; i < items.length; i += size) {
    chunkFn(items.slice(i, i + size));
    await new Promise((r) => setTimeout(r, 0));  // 让出主线程
  }
}
```

### 2. MessageChannel(更精准的让出)

`setTimeout(0)` 有 4ms 最小延迟(嵌套),`MessageChannel` 是真正的"宏任务让出",更精准:

```js
const channel = new MessageChannel();
const port = channel.port2;
channel.port1.onmessage = () => {/* 下一批 */};
// 让出:port.postMessage(null)
```

### 3. requestIdleCallback(空闲时处理)

```js
requestIdleCallback((deadline) => {
  while (deadline.timeRemaining() > 0 && tasks.length) {
    run(tasks.shift());
  }
});
```

### 4. Web Worker(重计算彻底移出主线程)

```js
const worker = new Worker("calc.js");
worker.postMessage({ n: 1e8 });
worker.onmessage = (e) => console.log(e.data);   // 主线程全程不卡
```

**为什么让出主线程能"不卡"?** 浏览器渲染、响应输入都要主线程;长任务占满它,渲染与点击就排队。切碎后穿插让出,浏览器得以处理输入与渲染(呼应 [1.8](/卷一-JavaScript语言内核/1.8-深入事件循环))。

## 三、虚拟滚动(长列表的终极方案)

**问题**:几万条数据一次性渲染 = 几万个 DOM 节点,首帧和滚动都卡。

**原理**:只渲染**可视区**内的少量项,滚动时用 `translateY` 偏移 + 顶部占位高度模拟"完整列表"。

```mermaid
flowchart LR
    A[数据 5 万条] --> B[只渲染可视区 ~20 条]
    B --> C[顶部占位 div 撑起总高度]
    C --> D[滚动时 translateY 偏移可视项]
```

```js
// 虚拟滚动骨架(简化)
function VirtualList({ items, itemHeight, viewportHeight }) {
  const [scrollTop, setScrollTop] = useState(0);
  const start = Math.floor(scrollTop / itemHeight);          // 起始索引
  const visibleCount = Math.ceil(viewportHeight / itemHeight) + 2; // 可视数量 + 缓冲
  const visibleItems = items.slice(start, start + visibleCount);

  return (
    <div style={{ height: viewportHeight, overflow: "auto" }} onScroll={e => setScrollTop(e.target.scrollTop)}>
      <div style={{ height: items.length * itemHeight, position: "relative" }}>
        <div style={{ transform: `translateY(${start * itemHeight}px)` }}>
          {visibleItems.map((item, i) => <div key={start + i} style={{ height: itemHeight }}>{item}</div>)}
        </div>
      </div>
    </div>
  );
}
```

> 关键:① 顶部容器总高度 = `items.length × itemHeight` 撑出滚动条;② 只渲染 `start ~ start+visibleCount` 这一小段;③ 用 `translateY` 把可见项定位到正确位置。DOM 数量从 O(n) 降到 O(可视区)。

## 四、首屏渲染优化(清单)

| 手段 | 说明 |
|------|------|
| JS 不阻塞 | `defer`/`async`;同步 script 移到底部 |
| CSS 关键内联 | 首屏关键 CSS 内联到 HTML,其余延迟 |
| LCP 尽早 | 主内容别被 JS 阻塞、给高优先级(10.1/10.2) |
| SSR/SSG | 服务端出内容,首屏不白屏(6.6/7.7) |
| 减少首帧工作量 | 首屏只渲染必要组件,其余懒加载 |

## 五、小结

```
减少重排:读写分离/离线DOM/隐藏后改/transform动画
长任务:>50ms 阻塞交互;时间切片/MessageChannel/idleCallback/Worker
虚拟滚动:只渲染可视区,DOM 从 O(n)→O(可视区)
首屏:defer/async、关键CSS内联、LCP尽早、SSR
```

## 六、面试题

**Q1:什么场景需要"虚拟滚动"?原理?**

列表**极大**(几万条)时,一次性渲染海量 DOM 代价高。虚拟滚动**只渲染可视区少量项**,用 `translateY` + 占位高度模拟完整高度,渲染成本从 O(n) 降到 O(可视区)。

**Q2:如何定位"卡顿"是谁造成的?**

DevTools → Performance 录制 → 看**长任务(Long Task)**与火焰图,找到长占主线程的函数 → 拆分/丢 Worker/优化。**先定位再优化**。

**Q3:什么是"长任务"?为什么它影响 INP?**

**>50ms 的任务**叫长任务;它占满主线程,让用户点击/输入无法及时响应 → INP 变差。所以要拆分长任务。

**Q4:时间切片怎么"让出主线程"?为什么 `setTimeout(0)` 就行?**

把大任务切成小块,每块之间 `setTimeout(0)`/`MessageChannel` 让出,浏览器在间隙处理输入与渲染。本质:别让单个宏任务长期霸占主线程(1.8 事件循环)。

**Q5:为什么动画用 transform 而非 left?**

`left` 触发**重排**(样式→布局→绘制→合成),占主线程;`transform` 只走**合成**(2.5),合成线程/GPU 完成,不占主线程、不掉帧。

**Q6:读写分离为什么能减少重排?**

写样式只"标脏"、合并批处理;读布局属性会**强制立即重排**。读写交替 → 每次读都打断批处理、立即重排;读写分离 → 只重排一次。

**Q7:`setTimeout(0)` 和 `MessageChannel` 让出主线程,有什么区别?**

`setTimeout(0)` 有 **4ms 最小延迟**(嵌套超过 5 层),且受节流影响;`MessageChannel` 是**纯宏任务让出**,无 4ms 延迟、更精准。做"时间切片"时 `MessageChannel` 是更优选择(React Scheduler 早期就用它)。

**Q8:虚拟滚动如何处理"不定高"的列表项?**

固定高度最简;不定高需**测量**:① 先估算高度渲染,滚动到附近再测量修正;② 或用 `ResizeObserver` 记录每项真实高度,维护一个"累积高度前缀和"用于定位。核心是"**维护每项高度 + 前缀和**",而非硬编码固定值。
