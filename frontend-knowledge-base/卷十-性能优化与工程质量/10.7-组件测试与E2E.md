## 一、组件测试:按"用户"而非"实现"测

**Testing Library** 的核心理念:测试应该像**用户看到的那样**去断言(找文本/角色),而非查内部 state。

```jsx
// Vue Testing Library 示例思路
import { render, screen, fireEvent } from "@testing-library/vue";
import Counter from "./Counter.vue";

render(Counter);
fireEvent.click(screen.getByRole("button"));
expect(screen.getByText("1")).toBeTruthy();   // 断言"屏幕上显示 1",而非内部 state
```

**查询优先级(从高到低):**

```
getByRole(角色) > getByLabelText(标签) > getByText(文本) > getByTestId(兜底)
```

> 为什么优先 role?因为**可访问性**好的组件天然有 role,按 role 测 = 顺便测了 a11y;而 `testId` 是"看不到"的实现细节,应最后才用。

## 二、E2E:Playwright(端到端)

```js
import { test, expect } from "@playwright/test";

test("用户能登录", async ({ page }) => {
  await page.goto("/login");
  await page.fill('[name="email"]', "a@b.com");
  await page.click("button[type=submit]");
  await expect(page.getByText("欢迎")).toBeVisible();
});
```

- 多浏览器(Chromium/Firefox/WebKit)、自动等待、**录制**生成脚本
- 视觉回归:`expect(page).toHaveScreenshot()` 对比像素
- CI 集成、并行跑

## 三、测试选型

| 层 | 工具 | 测什么 | 数量 |
|----|------|--------|------|
| 单元 | Vitest | 纯逻辑、函数 | 多 |
| 组件 | Testing Library | 组件交互、渲染 | 中 |
| E2E | Playwright | 完整用户流程 | 少 |

## 小结

```
组件测试:按用户视角(role/text)断言,testId 兜底
E2E:Playwright 真实浏览器、自动等待、可视化/录制
比例:单元多 > 组件中 > E2E 少
```

## 面试题

**Q1:组件测试为什么要"按 role 查询"而非 testId?**

按 role/text 查询**贴近用户真实感知**,且天然覆盖**可访问性**(role 缺失说明 a11y 有问题);testId 是内部实现细节,变化频繁、还测不到真实体验。原则:**能 role 就别 testId**。

**Q2:Playwright 相比 Cypress 的优势?**

都做 E2E,Playwright 支持**更多浏览器**(含 WebKit)、**自动等待**更强、原生**并行 + 录制 + 视觉回归**,对现代 Web 特性(多标签、网络拦截)支持更好,且免费开源无商业限制。
