# 10.7 组件测试与 E2E(Testing Library / Playwright)

## 引言:按"用户"而非"实现"测

深挖要懂 **Testing Library 的查询优先级** 与 Playwright 的自动等待。这一章把组件测试和 E2E 的写法讲成能直接上手的样子。

---

## 一、组件测试:按用户视角

```jsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import Counter from "./Counter";

render(<Counter />);
await userEvent.click(screen.getByRole("button", { name: /增加/ }));
expect(screen.getByText("1")).toBeInTheDocument();
```

### 1. 查询优先级(从高到低)

```
getByRole(角色)> getByLabelText(标签)> getByPlaceholderText(占位)> getByText(文本)> getByTestId(兜底)
```

**为什么 role 优先?** 可访问性好的组件天然有 role,按 role 测 = **顺便测了 a11y**;`testId` 是"看不到"的实现细节,应最后才用。这就是"按用户而非实现测"的落地。

### 2. 三种查询变体(get / query / find)

| 变体 | 找不到时 | 用途 |
|------|---------|------|
| `getBy...` | 抛错 | 断言"一定存在" |
| `queryBy...` | 返回 null | 断言"不存在" |
| `findBy...` | 返回 reject 的 Promise | 断言"**异步**出现" |

```jsx
expect(screen.queryByText("加载中")).toBeNull();      // 不存在
const el = await screen.findByText("数据已加载");      // 异步等待出现
```

### 3. fireEvent vs userEvent

```jsx
fireEvent.change(input, { target: { value: "abc" } });   // 只触发单个事件
await userEvent.type(input, "abc");                       // 模拟真实输入(含 keydown/keyup/input 序列)
```

> `userEvent` 更接近**真实用户**行为(一次输入会触发一串事件),推荐优先用;`fireEvent` 更底层、快,用于精细控制。

### 4. 异步测试(waitFor)

```jsx
await waitFor(() => expect(screen.getByText("已提交")).toBeInTheDocument());
```

## 二、E2E:Playwright

### 1. 基础 + 多浏览器

```js
import { test, expect } from "@playwright/test";

test("用户能登录", async ({ page }) => {
  await page.goto("/login");
  await page.fill('[name="email"]', "a@b.com");
  await page.click("button[type=submit]");
  await expect(page.getByText("欢迎")).toBeVisible();
});
```

```bash
npx playwright test --project=chromium   # 指定浏览器
# playwright.config 里可配 chromium/firefox/webkit 多项目
```

### 2. 自动等待(核心优势)

**为什么自动等待重要?** 传统 E2E 要手动 `sleep` 等元素/网络;Playwright 的 `expect`/操作**自动重试直到条件满足**,大幅减少"flaky(偶发失败)"。

```js
await expect(page.getByText("结果")).toBeVisible();  // 自动等到出现,不用 sleep
```

### 3. 网络拦截(mock 接口)

```js
await page.route("**/api/users", (route) =>
  route.fulfill({ json: [{ id: 1, name: "Alice" }] })   // 拦截并返回假数据
);
```

### 4. 截图 / 视觉回归 / 录制

```js
await page.screenshot({ path: "home.png" });                 // 截图
await expect(page).toHaveScreenshot();                       // 视觉回归(对比像素快照)
```

```bash
npx playwright codegen https://example.com   # 录制:操作自动生成测试代码
```

## 三、选型

| 层 | 工具 | 数量 | 测什么 |
|----|------|------|--------|
| 单元 | Vitest | 多 | 纯逻辑、函数 |
| 组件 | Testing Library | 中 | 渲染 + 交互(用户视角) |
| E2E | Playwright | 少 | 完整用户旅程 |

> 比例:**单元多 > 组件中 > E2E 少**。E2E 只测核心旅程,不测每个分支。

---

## 四、小结

```
组件测试:按用户视角(role/text);get/query/find 三变体;userEvent 优于 fireEvent
E2E:Playwright 多浏览器、自动等待、网络 mock、视觉回归、录制
比例:单元多 > 组件中 > E2E 少
```

## 五、面试题

**Q1:组件测试为什么按 role 查询而非 testId?**

按 role/text **贴近用户感知**、天然覆盖 a11y;testId 是内部实现、变化频繁、测不到真实体验。**能 role 就别 testId**。

**Q2:Playwright 相比 Cypress 的优势?**

支持**更多浏览器**(含 WebKit)、**自动等待**更强、原生**并行 + 录制 + 视觉回归**,对现代 Web(多标签/网络拦截)支持更好。

**Q3:什么是"flaky test"?如何减少?**

**偶发失败**的测试(依赖时序/竞态)。减少:用**自动等待**(Playwright 的 expect 重试)、避免硬编码 `sleep`、测试隔离、稳定选择器。

**Q4:E2E 测试为什么"少而慢"?适合测什么?**

E2E 跑真实浏览器 + 完整流程,慢且脆、维护贵。适合测**核心用户旅程**(登录/下单),不适合测每个分支。

**Q5:视觉回归测试是什么?**

用 Playwright 的 `toHaveScreenshot` 对比页面**像素快照**,捕获"意外视觉变化"。适合 UI 库/组件库防样式回归。

**Q6:组件测试和单元测试的边界?**

单元测**纯逻辑**(函数、工具);组件测**渲染 + 交互**(按用户视角断言 DOM)。组件测试更接近"用户看到什么",单元测试更接近"函数返回什么"。

**Q7:`getBy`、`queryBy`、`findBy` 三者的区别?**

`getBy` 找不到就**抛错**(断言存在);`queryBy` 找不到返回 **null**(断言不存在);`findBy` 返回 **Promise**(异步等待出现)。按"同步存在/不存在/异步"三种需求选。

**Q8:`fireEvent` 和 `userEvent` 的区别?为什么推荐 userEvent?**

`fireEvent` 只触发**单个**事件;`userEvent` 模拟**真实用户行为**(输入会触发 keydown→keyup→input 一串事件)。userEvent 更接近真实、能测到"事件序列"的交互,推荐优先用。
