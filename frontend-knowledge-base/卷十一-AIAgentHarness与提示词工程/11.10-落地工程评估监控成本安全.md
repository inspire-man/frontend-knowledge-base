# 11.10 落地工程:评估 / 监控 / 成本 / 安全

> 卷:卷十一 · AI Agent Harness 与提示词工程
> 阅读时间:20min

---

## 引言:从"能跑"到"敢上线"的最后一步

Demo 能跑 ≠ 生产能用。企业 AI 落地 90% 卡在工程化:不会评估、不敢监控、成本失控、安全没底。这一章把"上线前必须想清楚的四个问题"讲透。

---

## 一、评估(Eval):怎么知道 Agent 干得好不好

| 方法 | 做法 | 适用 |
|------|------|------|
| **人工评估** | 抽样本人工打分(准确/相关/有用) | 上线前小规模 |
| **LLM-as-judge** | 用更强的模型给回答打分 | 规模化自动评估 |
| **基准集** | 预置"问题 → 期望答案 → 应命中文档" | 回归测试、持续监控 |
| **检索评测** | Recall@k / MRR | 单独评估检索质量 |

> **铁律:没有 eval 就别上线。** 至少要有"一撮带标准答案的问题集",每次改 prompt/模型/分块都能跑一遍,防止"越改越差"。

---

## 二、监控(上线后的眼睛)

| 指标 | 含义 | 告警 |
|------|------|------|
| 成功率 | 完成任务/总请求 | 突降 |
| 延迟 | P50/P95 响应时间 | 突增 |
| token 用量 | 单次对话 token 数 | 失控 |
| 成本 | 每请求/每用户成本 | 超预算 |
| 用户反馈 | 👍/👎、重试率 | 差评上升 |

> 至少监控"成功率 + 延迟 + 成本"三项,配合日志追踪(11.3 的观测)。

---

## 三、成本控制(呼应 11.3)

1. **模型分级**:简单步骤用便宜小模型,难步骤才上大模型
2. **上下文裁剪**:压缩历史、只保留决策结论(11.4)
3. **缓存**:相同/相似请求命中缓存,不重复调 LLM
4. **步数上限**:防无限循环烧钱(11.2)

---

## 四、安全加固(呼应 11.5)

| 风险 | 防护 |
|------|------|
| 提示注入 | 工具只信校验后的参数与白名单;不执行模型输出的自由指令 |
| 数据泄露 | 敏感数据不喂模型 / 脱敏;权限最小化 |
| 越权操作 | 高风险动作(删/发/支付)人工确认 |
| 沙箱 | 代码执行、文件操作隔离运行 |

---

## 五、落地路线图(一句话概括)

```
先选场景(知识库问答/客服/代码) → 搭最小闭环 → 建 eval 基准集
→ 上线灰度 + 监控 → 按数据迭代(改 prompt/分块/模型) → 逐步放量
```

> 核心心法:**先跑通再优化,先评估再上线,先监控再放量。**

---

## 六、小结

```
落地四问:评估(eval 基准集 + LLM-as-judge)/ 监控(成功率·延迟·成本)/ 成本(分级·缓存·裁剪)/ 安全(防注入·脱敏·人审)
路线:选场景 → 最小闭环 → eval → 灰度监控 → 迭代放量
```

## 七、面试/实践要点

**Q1:为什么说"没有 eval 就别上线"?**

LLM 是非确定性的,改 prompt/模型/分块都可能让质量悄悄变差。没有 eval 基准集,你无法发现"越改越差",也无法回滚。eval 是"可观测的质量"。

**Q2:LLM-as-judge 是什么?可靠吗?**

用一个(通常更强的)模型当"裁判",给回答打分(准确/相关/是否有幻觉)。优点是能规模化自动评估;缺点是裁判本身也可能有偏见,需与人工评估交叉验证。

**Q3:生产 Agent 的成本主要花在哪?怎么控?**

大头在**每轮对话的 token 消耗**(尤其长上下文)。控法:模型分级(小模型干粗活)、上下文裁剪(压缩历史)、缓存命中、步数上限——四管齐下,成本能降一个数量级。
