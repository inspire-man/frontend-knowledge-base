# 11.6 提示词工程(上):指令与结构

> 卷:卷十一 · AI Agent Harness 与提示词工程
> 难度:⭐⭐ 进阶 | 阅读时间:25min

---

## 引言:提示词 = 把"意图 + 约束"写进上下文的输入

提示词工程(Prompt Engineering)不是"会写套话",而是**用结构化方式,把任务、约束、格式讲清楚,引导模型输出你想要的东西**。上半部分讲"指令与结构",下半部分(11.7)讲"推理增强"。

---

## 一、一个好提示词的结构骨架

```
① 角色(Role):你是谁,以什么视角做事
② 任务(Task):要做什么,目标是什么
③ 上下文(Context):必要的背景、约束条件
④ 约束(Constraints):边界——不许做什么、格式要求
⑤ 输出格式(Output):结果长什么样(JSON/表格/步骤)
```

```markdown
你是资深前端工程师(角色)。
帮我审查下面这段代码的性能问题(任务)。
背景:这是一个 Vue3 项目,目标浏览器是移动端(上下文)。
要求:只指出问题,不直接改代码;每条给出"问题-原因-建议"(约束)。
输出:Markdown 表格,列为【问题|原因|建议】(输出格式)。
```

## 二、指令遵循的四个要点

| 要点 | 说明 | 反例 |
|------|------|------|
| **具体** | 越具体,越可控 | "写点东西" ❌ |
| **给边界** | 明确"不要做什么" | 只说不许废话,没说长度 |
| **给格式** | 指定输出结构 | 期望 JSON 却没说 |
| **给示例** | few-shot 示范 | 任务新颖却零示例 |

> 一个反直觉的经验:**约束(negative)往往比指令(positive)更能压住幻觉**——"不要编造 API,不知道就说不知道"这类"负面指令"很关键(呼应 11.1 的幻觉)。

---

## 三、输出格式约束:让结果"可解析"

Agent 场景里,模型的输出经常要被**程序解析**。所以要:

1. **指定格式**:JSON、XML、Markdown、或自定义标记
2. **配低温**(11.1):降低随机性,提高格式稳定
3. **用工具的 JSON Schema 硬约束**(11.5):函数调用的结构化输出是最稳的

```markdown
只输出一个 JSON 对象,不要任何其他文字:
{"result": "通过/不通过", "reason": "一句话原因"}
```

> 原则:**凡是下游要解析的输出,都要锁格式**——口头"大概输出个 JSON"一定会翻车。

---

## 四、few-shot:用示例"编程"行为

不给模型改权重,只靠**在上下文里放示例**,就能教会它格式与风格(11.1 的上下文学习):

```markdown
把句子分类为"正面/负面":
"太棒了" → 正面
"真烂" → 负面
"还行吧" →           ← 模型按示例模式补出"中性/正面"
```

**few-shot 的三个技巧:**

- 示例要**覆盖边界情况**(正面、负面、中性都来一个)
- 示例与目标任务**格式严格一致**
- 示例不是越多越好:**关键示例 > 一堆平庸示例**

---

## 五、小结

```
提示词结构:角色 + 任务 + 上下文 + 约束 + 输出格式
指令遵循:具体 / 给边界(负面约束压幻觉)/ 给格式 / 给示例
输出格式:JSON 化 + 低温 + 结构化输出;要解析必锁格式
few-shot:示例即"上下文里的编程",覆盖边界、格式一致
```

## 六、思考题

**Q1:为什么"负面约束"("不要编造""不知道就说不知道")很重要?**

因为模型是"概率补全"而非"查库",默认倾向**给一个看似合理的答案**(幻觉)。正面指令告诉它"做什么",负面约束告诉它"**做不出来的边界在哪**",能显著抑制它在没把握时乱编。这是提示词工程里最被低估的一类。

**Q2:让模型稳定输出 JSON,有哪些手段?**

① 提示里**明确指定** JSON 结构与字段;② 调**低 temperature**(降低随机);③ 用**结构化输出/函数调用**的 schema 硬约束(最稳);④ few-shot 给 JSON 示例;⑤ 解析失败时**把错误喂回重试**(11.3)。
