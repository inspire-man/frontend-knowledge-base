# 2.2 导航与资源加载(URL → 首帧)

> 卷:卷二 · 浏览器工作原理
> 难度:⭐⭐ 进阶 | 阅读时间:25min | 状态:进行中

---

## 引言:一道必考题,一条完整链路

"从输入 URL 到页面显示,发生了什么?"是前端第一高频面试题。它考的不是背诵,而是把**网络 + 进程 + 渲染**串起来的能力。本章给出可分层讲述的完整版。(细节术语在 2.3 渲染管线展开。)

---

## 一、总览:一条时间线

```
地址栏输入 → URL 处理 → DNS 解析 → TCP 连接 → TLS 握手(HTTPS)
→ 发送请求 → 服务器响应 → 解析响应 → 构建 DOM/CSSOM
→ 布局 → 分层 → 绘制 → 光栅化 → 合成 → 显示
```

---

## 二、阶段 1:URL 处理(浏览器主进程)

1. **补全协议**:输入 `baidu.com` → 补成 `https://baidu.com`
2. **编码**:非 ASCII 字符(如中文)自动做 **URL 编码(百分号编码)**
3. **交给网络进程**去发起请求

---

## 三、阶段 2:网络请求(网络进程)

```
DNS 查询(域名 → IP)
  → TCP 三次握手(建立可靠连接)
  → TLS 协商(HTTPS 加密握手)
  → 发送 HTTP 请求
  → 服务器响应(状态码 + 响应头 + 响应体)
```

关键点:

- **DNS**:域名解析成 IP,有 DNS 缓存(浏览器/系统/路由器/本地 hosts)加速
- **TCP 三次握手**:SYN → SYN-ACK → ACK,建立连接
- **HTTPS**:额外一次 TLS 握手,协商加密密钥(详见卷四 4.4)
- 收到响应后,**先看响应头 `Content-Type`** 决定怎么做

---

## 四、阶段 3:解析响应,分流处理

| `Content-Type` | 浏览器动作 |
|----------------|-----------|
| `text/html` | 交给**渲染进程**,开始解析 HTML |
| `text/css` | 当作样式表 |
| `application/javascript` | 交给 JS 引擎执行 |
| `image/*` | 当作图片渲染 |
| `application/octet-stream` / `attachment` | 触发**下载** |

> 前端最关心的是 `text/html`:它会**提交导航(commit navigation)**,正式启动渲染进程开始造页面。

---

## 五、阶段 4:构建 DOM 与 CSSOM(渲染主线程)

1. 解析 HTML,边下载边解析,遇到:
   - `<link>`(CSS)→ **交给其他线程下载,不阻塞解析**,但 CSS 没就绪会**阻塞渲染**
   - `<script>`(JS)→ **阻塞解析**(除非 async/defer),因为 JS 可能插入/修改 DOM
2. 产出两棵树:
   - **DOM 树**(文档结构)
   - **CSSOM 树**(样式结构)

**关键易错点:**

```html
<script>   <!-- ⚠️ 读到它会停下解析 HTML,等 JS 下载+执行完 -->
```

**为什么 CSS 阻塞渲染?**
即使 CSS 下载是异步的,但"渲染"要等 CSSOM 就绪才能进行——否则页面会闪一下"没样式的裸 HTML"(FOUC)。所以:
- **CSS 不阻塞 DOM 构建,但阻塞渲染**
- **JS 阻塞 DOM 解析**(同步 script),`async`/`defer` 可缓解(见下)

| 属性 | 下载 | 执行时机 | 阻塞解析 |
|------|------|---------|---------|
| 无 | 阻塞 | 下载完立即执行 | ⚠️ 阻塞 |
| `defer` | 异步 | DOM 解析完后、DOMContentLoaded 前按序执行 | 不阻塞 |
| `async` | 异步 | 下载完就执行(乱序) | 执行瞬间仍短暂阻塞 |

---

## 六、阶段 5:布局 → 分层 → 绘制 → 光栅化 → 合成

DOM + CSSOM 就绪后(详见 2.3):

```
样式计算(computed style)→ 布局树(位置) → 分层 → 绘制(指令)
→ 光栅化(位图) → 合成(提交 GPU)→ 显示
```

---

## 七、用一句话把面试答出层次

> **"输入 URL 后:主进程先处理补全与编码,交给网络进程做 DNS → TCP → TLS → HTTP 请求;响应回来按 Content-Type 分流,text/html 提交导航到渲染进程;渲染主线程解析 HTML/CSS 构建 DOM 与 CSSOM(JS 会阻塞解析,CSS 阻塞渲染),然后计算样式、布局、分层、绘制、光栅化、合成,最终显示。"**

能讲到"**进程分工 + 解析阻塞 + 合成结束**"这三点,就已经碾压 80% 的答案。

---

## 八、小结

```
URL 输入 → 主进程(补全/编码)
        → 网络进程(DNS → TCP → TLS → HTTP → 响应)
        → 按 Content-Type 分流(text/html → 提交导航)
        → 渲染主线程(DOM + CSSOM;JS 阻塞解析,CSS 阻塞渲染)
        → 布局 → 分层 → 绘制 → 光栅化 → 合成 → 显示
```

## 九、面试题

**Q1:`defer` 和 `async` 的区别?**

`defer`:异步下载,`DOMContentLoaded` 之前、按文档顺序执行,保证顺序 → 适合依赖执行顺序的脚本。`async`:下载完立刻执行,执行顺序不定 → 适合无依赖的独立脚本(如埋点、广告)。两者都不阻塞 HTML 解析(但 `async` 执行那一刻会短暂阻塞)。

**Q2:为什么把 `<script>` 放 `</body>` 前能"更快看到页面"?**

因为同步 script 会阻塞 DOM 解析:放 `<head>` 里,浏览器要等脚本下载+执行完才开始渲染 body;放底部,先解析渲染完页面结构,再执行脚本,首屏更快。现代更优解:用 `defer` + 放 head,兼顾顺序与不阻塞。
