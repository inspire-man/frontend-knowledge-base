## 引言:JS 代码到底怎么"跑"起来的,内存又怎么收

V8 是 Chrome 与 Node 共用的 JS 引擎。搞懂它的**解释 + 即时编译(JIT)**机制和**分代垃圾回收**,能解释很多性能现象,也能在线上"内存蹭蹭涨"时知道去哪查。

---

## 一、V8 执行流程:解释器 + 优化编译器

```
源码 → Parser 解析 → AST 抽象语法树
        │
        ▼
Ignition(解释器)──▶ 字节码(Bytecode)──逐条解释执行
        │                    ▲
        │ 热点函数(频繁执行)  │ 反馈优化信息(类型稳定等)
        ▼                    │
TurboFan(优化编译器)─────▶ 机器码(更快)
        │
        ▼(若"假设"失效,如类型变了)→ 反优化(Deoptimization)回到字节码
```

关键点:

- **不是纯解释、也不是纯编译**:先用解释器快速启动,再对**热点代码**做 JIT 编译成机器码加速
- **"隐藏类/内联缓存"优化**:对象形状稳定时快;反复给对象增删属性/改类型,会触发**反优化**,反而变慢

```js
// 坏味道:同一个对象反复换形状,破坏 V8 优化
const o = {};
o.a = 1;
o.b = 2;   // 形状不断变,类型反馈不稳定 → 可能反优化
```

> 工程启示:**保持对象结构一致**(初始化时就定好字段),别天马行空地增删属性。

## 二、内存结构:栈与堆(呼应 1.1)

| 区域 | 存什么 | 特点 |
|------|--------|------|
| 栈(Stack) | 原始值、函数调用帧、对象**引用** | 小而快,后进先出,自动释放 |
| 堆(Heap) | 对象、数组、函数、闭包环境等 | 大而慢,由 **GC** 管理 |

> 我们在 1.1 说的"原始值存栈、引用值存堆"在这里有了引擎层面的印证。

---

## 三、垃圾回收(GC):分代回收

V8 用**分代**策略:大多数对象"朝生暮死",少数长命。于是:

### 1. 新生代(Young Generation / Scavenger)

- 存**存活时间短**的对象
- 用 **Scavenger** 算法(半空间复制):把活对象复制到另一半空间,整块清空旧区,快

### 2. 老生代(Old Generation)

- 新生代里**幸存多次**的对象被晋升到这里
- 用 **Mark-Sweep(标记-清除)** 找出活对象、清掉死对象;碎片多了用 **Mark-Compact(标记-整理)** 压缩
- 为减少停顿,采用**增量标记**、**并发标记**:把标记任务切成小片,穿插在执行里跑,避免长时间"全停顿(stop-the-world)"

## 四、内存泄漏:识别与排查

### 常见泄漏原因

| 场景 | 说明 |
|------|------|
| **全局变量** | 意外挂在 window 上的大对象永远收不回来 |
| **闭包引用** | 闭包长期持有大对象不放(见 1.7 的代价) |
| **未清理的定时器/监听器** | `setInterval`、`addEventListener` 忘 `clearTimeout`/`removeEventListener` |
| **游离的 DOM 引用** | JS 变量仍引用已删除的 DOM 节点,节点无法回收 |
| **Map/缓存无限增长** | 用普通 Map 做缓存越塞越多;应换 `WeakMap`/LRU |

### 如何排查(DevTools)

1. **Performance 面板**:录制 → 观察堆曲线,若**"锯齿不回落"(整体持续爬升)**,疑似泄漏
2. **Memory 面板 → Heap Snapshot**:对可疑操作前后各拍一张快照,对比 **Delta**,看哪些对象数量异常增长
3. **Memory → Allocation instrumentation**:看**谁在持续分配内存**

> 三板斧先看:`setInterval/监听器有没有清理`、`闭包有没有长期持有大对象`、`缓存有没有上限`。

## 五、小结

```
V8 执行:源码 → AST → 字节码(Ignition)→ 热点 JIT(TurboFan)→ 机器码
        (类型/形状不稳定 → 反优化回字节码 → 变慢)

内存:栈(原始值/引用)+ 堆(对象,GC 管理)
GC:分代 —— 新生代(Scavenger 复制)、老生代(Mark-Sweep/Compact,增量并发减小停顿)

泄漏三大来源:全局/闭包/未清理的定时器与监听器 → 用 Memory 快照对比排查
```

## 六、面试题

**Q1:什么是 JIT?V8 为什么不用纯解释或纯编译?**

JIT(即时编译):先用解释器**快速启动**(低延迟),运行时识别**热点代码**,再编译成机器码**加速**(高吞吐)。纯解释启动快但长期慢,纯编译启动慢但长期快;JIT 用"解释 + 局部编译 + 反优化兜底"兼顾两者。

**Q2:为什么推荐用 `WeakMap` 做缓存,而不是 `Map`?**

`Map` 的键是**强引用**,只要 Map 还活着,键对象就永远不被回收 → 缓存无限增长、内存泄漏。`WeakMap` 的键是**弱引用**,键对象无其他引用时会被 GC 回收,缓存随之"自动失效",不会堆积(见 1.7)。

**Q3:泄漏和"内存占用高"是一回事吗?**

不是。**占用高**可能是合理的大数据;**泄漏**是"本该回收、却持续增长不回落"。判断靠观测:堆曲线只涨不落、快照对比对象数量异常增长。
