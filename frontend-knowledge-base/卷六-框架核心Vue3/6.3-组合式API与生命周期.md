# 6.3 组合式 API 与生命周期

> 卷:卷六 · 框架核心 · Vue3
> 阅读时间:25min

---

## 引言:从"散落各处的选项"到"按逻辑聚合"

Options API 把同一功能的代码拆到 data/methods/computed 各处,功能一大就"东一榔头西一棒"。组合式 API 把**同一逻辑写在一起**。深挖要懂它为什么对 TS 更友好、以及 composable 为何优于 mixin。

---

## 一、为什么需要组合式 API

```js
// Options API:搜索功能散落四处
data() { return { keyword: "", results: [] }; },
methods: { async doSearch() {...} },
computed: { hasResult() {...} },
watch: { keyword() {...} },
```

```js
// 组合式:逻辑聚合
function useSearch() {
  const keyword = ref("");
  const hasResult = computed(() => results.value.length > 0);
  async function doSearch() {...}
  watch(keyword, doSearch);
  return { keyword, hasResult, doSearch };
}
```

---

## 二、为什么组合式对 TS 更友好(底层)

> Options API 里 `this` 的值要靠 Vue 内部类型魔法推断,**跨选项的类型传递脆弱**;组合式 API 是**普通函数 + 普通变量**,`ref`/`computed` 返回的值**类型直接可推、可跨函数传递**,类型天然清晰。这是它被 TS 用户偏好、也是尤雨溪力推的根因。

---

## 三、composable vs mixin(关键对比)

| | Composable | Mixin |
|---|-----------|-------|
| 命名空间 | 显式解构,来源清晰 | 隐式合并,命名易冲突 |
| 来源追踪 | 可追溯 | 难(不知道来自哪个 mixin) |
| 类型 | 好推 | 差 |

> **为什么 composable 优于 mixin?** mixin 是"**暗箱合并**"——多个 mixin 的同名属性/方法会静默覆盖,来源不可追;composable 是"**显式解构 + 普通函数**",依赖关系清晰、类型可推、无冲突。

---

## 四、生命周期:选项式 ↔ 组合式

| 选项式 | 组合式 |
|--------|--------|
| `beforeCreate` / `created` | 无需(setup 即此时机) |
| `beforeMount` | `onBeforeMount` |
| `mounted` | `onMounted` |
| `beforeUnmount` | `onBeforeUnmount` |
| `unmounted` | `onUnmounted` |

> 组合式**去掉 beforeCreate/created**(setup 本身就在这两者之间执行),其余加 `on` 前缀。

---

## 五、小结

```
组合式:按"逻辑关注点"组织(setup + 组合函数)
vs Options:逻辑聚合、可复用、类型推导好
composable 优于 mixin:显式、可追溯、无命名冲突
生命周期:on 前缀,无 beforeCreate/created
```

## 六、面试题

**Q1:为什么 Vue3 引入组合式 API?比 Options 好在哪?**

① **逻辑聚合**;② **可复用**(composable 优于 mixin);③ **类型推导更好**(普通函数+变量);④ 功能复杂时不再"选项越长越乱"。

**Q2:watch 和 watchEffect 的区别?**

`watch` 需**显式指定**侦听源,能拿新旧值、配 immediate/deep;`watchEffect` **自动追踪**依赖、立即执行一次,但不直接给旧值。能写清就用 watchEffect,要旧值/精确控制用 watch。

**Q3:composable 为什么优于 mixin?**

mixin 是**暗箱合并**(同名静默覆盖、来源不可追);composable 是**显式解构 + 普通函数**,依赖清晰、类型可推、无冲突。这是组合式复用的主流范式。

**Q4:为什么组合式 API 里没有 beforeCreate/created?**

因为 `setup()` 的**执行时机就在 beforeCreate 和 created 之间**,setup 里的代码本身就等价于这两个钩子,没必要再单设(逻辑放 setup 顶部即可)。

**Q5:组件卸载时如何做清理?哪些要清理?**

用 `onUnmounted`/`onBeforeUnmount` 注册清理;`watch`/`watchEffect` 的返回是停止函数。清理:事件监听、定时器、订阅,防止内存泄漏(呼应 [2.6](/卷二-浏览器工作原理/2.6-V8引擎与内存))。

**Q6:`<script setup>` 相比手写 setup() 有什么优势?**

编译期糖:省去 `setup() { return {...} }` 样板、变量模板自动暴露、**响应式 props 解构**(3.5+)、更好的类型与自动 import,开发体验更好。
