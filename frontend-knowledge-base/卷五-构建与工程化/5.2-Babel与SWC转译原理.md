# 5.2 Babel / SWC 转译原理

## 引言:为什么需要"转译"

浏览器能跑的 JS 有限:新语法、超集语法(JSX/TS)不能直接跑。转译器把它们变成兼容代码。这条路走过 **Babel → SWC/esbuild** 两代。深挖要懂 **AST 工作流** 与 **语法转译 vs polyfill 的分野**。

---

## 一、转译器干三件事

1. **语法转换**:新语法 → 旧语法(`?.` → 判断)
2. **polyfill**:补缺失 API(`Promise`、`includes`)
3. **能力扩展**:JSX/TS → JS

```js
const f = (a = 1) => a ** 2;
// ↓ 转译后
var f = function (a) {
  return Math.pow(a === undefined ? 1 : a, 2);
};
```

---

## 二、AST(抽象语法树)

### 2.1 什么是 AST

转译器不是"字符串替换",而是先把源码解析成**抽象语法树(AST,Abstract Syntax Tree)**,在树上做变换,再生成代码。字符串替换太脆弱(分不清"是语法还是字符串里的内容")。

### 2.2 一个箭头函数的 AST

```js
// 源码
const add = (a, b) => a + b;
```

它的 AST(简化)大致长这样:

```json
{
  "type": "VariableDeclaration",
  "kind": "const",
  "declarations": [{
    "id": { "type": "Identifier", "name": "add" },
    "init": {
      "type": "ArrowFunctionExpression",
      "params": [
        { "type": "Identifier", "name": "a" },
        { "type": "Identifier", "name": "b" }
      ],
      "body": {
        "type": "BinaryExpression",
        "operator": "+",
        "left": { "type": "Identifier", "name": "a" },
        "right": { "type": "Identifier", "name": "b" }
      }
    }
  }]
}
```

> 转译器要做的,就是把 `ArrowFunctionExpression` 节点**替换**成 `FunctionExpression` 节点。改的是**树的结构**,不是文本。

---

## 三、Babel 工作流(parse → transform → generate)

```mermaid
flowchart LR
    A[源码] -->|parse| B[AST]
    B -->|transform 插件| C[新 AST]
    C -->|generate| D[目标代码]
```

- **Parser**:源码 → AST(`@babel/parser`)
- **Transform**:插件遍历/改 AST(核心,`@babel/traverse`)
- **Generator**:AST → 代码(`@babel/generator`)

---

## 四、preset vs plugin + browserslist

```json
{
  "presets": [["@babel/preset-env", {
    "targets": "> 1%, last 2 versions, not dead"
  }]],
  "plugins": ["@babel/plugin-transform-arrow-functions"]
}
```

> **preset = 一组 plugin 的集合**。`preset-env` 根据 `targets`(browserslist 语法)**按需**引入转换,避免过度编译。

**browserslist 查询语法:**

```json
"> 1%"                    // 全球使用率 > 1% 的浏览器
"last 2 versions"         // 每个浏览器最近 2 个版本
"not dead"                // 排除官方已停止维护的浏览器
"> 1%, not IE 11"         // 组合
```

## 五、手写一个 Babel 插件

插件就是**遍历 AST 的 visitor 对象**:

```js
// 把 const 换成 var 的极简插件
module.exports = function () {
  return {
    visitor: {
      VariableDeclaration(path) {
        if (path.node.kind === "const") {
          path.node.kind = "var";       // 直接改 AST 节点
        }
      },
    },
  };
};
```

> 核心 API:`path.node` 是当前节点,`path.replaceWith()` 替换、`path.traverse()` 递归、`path.skip()` 跳过。插件生态基于这套 visitor 模式(访问者模式)。

## 六、语法转译 vs polyfill(底层分野)

### 6.1 分野

| | 语法转译 | polyfill |
|---|---------|----------|
| 改什么 | **语法结构** | **运行时 API** |
| 例子 | 箭头函数 → function | `Promise`/`includes` |
| 手段 | AST 变换 | 注入实现代码 |

> **关键认知**:语法能"改写",但 API(`Promise` 等)是"环境缺什么补什么",两者解决不同层面的兼容。

### 6.2 polyfill 的三种引入方式

```js
// ① 全量引入(最简单,体积大)
import "core-js/stable";
import "regenerator-runtime/runtime";

// ② entry:按 targets 引入该目标环境需要的全部
// preset-env 配 useBuiltIns: 'entry',入口手动 import core-js

// ③ usage:按代码"实际用到"的 API 自动引入(推荐,体积最小)
// preset-env 配 useBuiltIns: 'usage',自动分析注入
```

| 模式 | 体积 | 说明 |
|------|------|------|
| 全量 | 最大 | 一股脑全引 |
| `entry` | 中 | 按 targets 补 |
| `usage` | **最小** | 只补用到的 |

### 6.3 @babel/runtime + helpers(避免重复注入)

Babel 转译时会注入**辅助函数(helpers)**,如 `_extends`、`_objectSpread`。每个文件都注入一份会重复;用 `@babel/plugin-transform-runtime` 让它们统一从 `@babel/runtime` **引用**,而非每文件复制:

```json
{
  "plugins": [["@babel/plugin-transform-runtime", { "corejs": 3 }]]
}
```

> 好处:① 减小产物体积(helpers 共享);② 避免 polyfill **污染全局**(用模块引用而非挂 window)。

## 七、SWC / esbuild:用更快语言重写

| | Babel | SWC | esbuild |
|---|-------|-----|---------|
| 语言 | JS | Rust | Go |
| 速度 | 慢(基准) | 快 | **极快** |
| 生态 | **最强** | 中 | 少 |

### 7.1 SWC 配置(.swcrc)

```json
{
  "jsc": {
    "parser": { "syntax": "typescript", "tsx": true },
    "target": "es2015"
  },
  "module": { "type": "es6" }
}
```

### 7.2 为什么 esbuild 快那么多

esbuild 用 **Go** 编译到原生机器码、内部**并行**、复用 AST、少做抽象;而 Babel 是 **JS** 实现,跑在 JS 引擎上、插件模型层数多。这是"编译执行 vs 解释执行"的性能差距。

> 现状分工:Vite 用 esbuild 做**依赖预构建**,SWC 被 Next.js 采用;需**深度自定义插件**时 Babel 生态不可替代。三者常共存。

---

## 八、小结

```
转译 = 语法转换 + polyfill + 能力扩展(JSX/TS)
Babel:parse → transform(plugin/preset 遍历改 AST)→ generate
AST:抽象语法树,转译改的是"树"不是文本;visitor 模式写插件
语法转译(改结构)vs polyfill(补 API);core-js 三模式,usage 最小
演进:Babel(JS 全功能)→ SWC(Rust)/esbuild(Go,快 10~100 倍)
```

## 九、面试题

**Q1:`preset` 和 `plugin` 的区别?**

`plugin` 是**单个**转换能力(转箭头函数);`preset` 是**一组 plugin 的预设**(preset-env/preset-react)。执行顺序:plugin 先于 preset。

**Q2:语法转译和 polyfill 的区别?**

语法转译改**语法结构**(箭头→function);polyfill 补**运行时 API**(Promise/includes)。两者解决不同层面的兼容。

**Q3:为什么 esbuild 比 Babel 快那么多?**

esbuild 用 **Go** 编译到原生机器码、内部并行、复用 AST;Babel 是 **JS** 实现,跑在 JS 引擎、插件抽象层多。这是"编译执行 vs 解释执行"的性能差距。

**Q4:`useBuiltIns: 'usage'` 相比全量引入 polyfill 有什么好处?**

全量引入体积大;`usage` 会**分析代码实际用到的 API**,只引入对应 polyfill,体积最小。介于两者间的 `entry` 按 targets 补。

**Q5:什么场景还需要 Babel 而不是只用 esbuild/SWC?**

需要**深度自定义的 Babel 插件生态**(复杂代码生成、实验语法、特定 AST 变换)时,Babel 生态最全、最可扩展;esbuild/SWC 插件能力相对受限,适合"纯转译提速"。

**Q6:Babel 的 transform 阶段到底在做什么?**

在 **AST** 上运行插件:遍历节点(`traverse`),按规则**增删改 AST 节点**(如把箭头函数节点改成 function 节点),输出新 AST。改的是树,不是文本。

**Q7:`@babel/plugin-transform-runtime` 解决什么问题?**

Babel 转译会注入辅助函数(helpers),每个文件复制一份会重复、polyfill 还会**污染全局**。`transform-runtime` 让 helpers/polyfill 统一从 `@babel/runtime` **模块引用**,减小体积、不污染全局。

**Q8:Babel 插件的核心 API 是什么?简述写一个插件的思路?**

核心是 **visitor 模式**:定义 `visitor` 对象,键是 AST 节点类型,值是处理函数;通过 `path.node` 读改节点、`path.replaceWith()` 替换。思路:针对目标语法节点写 visitor,把它改成兼容节点。
