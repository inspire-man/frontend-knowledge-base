## 引言:为什么需要"转译"

浏览器能跑的 JS 有限制:新语法(ES2020+)、超集语法(JSX、TS)不能直接跑。转译器把它们变成**兼容的运行时代码**。这条路已走过 **Babel → SWC/esbuild** 两代。

---

## 一、转译器干的三件事

1. **语法转换**:新语法 → 旧语法(`?.` → `a == null ? ...`)
2. **polyfill**:补缺失的 API(`Promise`、`Array.includes`)
3. **能力扩展**:JSX/TS → JS

```js
// 输入(现代)
const f = (a = 1) => a ** 2;

// 输出(兼容)
var f = function (a) { return Math.pow(a === undefined ? 1 : a, 2); };
```

---

## 二、Babel 的工作流

```mermaid
flowchart LR
    A[源码] -->|parse| B[AST 抽象语法树]
    B -->|transform 插件| C[新 AST]
    C -->|generate| D[目标代码]
```

- **Parser**:源码 → AST(用 `@babel/parser`)
- **Transform**:插件遍历/修改 AST(核心环节,`@babel/traverse`)
- **Generator**:AST → 代码(用 `@babel/generator`)

**preset 与 plugin 的关系:**

```json
{
  "presets": [["@babel/preset-env", { "targets": "> 1%, last 2 versions" }]],
  "plugins": ["@babel/plugin-transform-arrow-functions"]
}
```

> **preset = 一组 plugin 的集合**。`preset-env` 会根据 `targets`(目标浏览器)**按需**引入转换,避免过度编译。

---

## 三、polyfill:补 API 而非语法

语法能转,但 API(`Promise`/`includes`)转不了语法,得"补":

```js
// 按需注入 polyfill(core-js)
import "core-js/stable";
// 或 preset-env 配 useBuiltIns: 'usage' 自动按用法引入
```

> 现代更推荐 `@babel/preset-env` + `core-js` 的 `usage` 模式:只引入你**实际用到**的 polyfill,体积最小。

---

## 四、SWC / esbuild:用"更快"的语言重写

Babel 纯 JS 实现,大项目启动慢。**SWC(Rust)/ esbuild(Go)** 用编译型语言重写,快 **10~100 倍**:

| | Babel | SWC | esbuild |
|---|-------|-----|---------|
| 语言 | JS | Rust | Go |
| 速度 | 慢(基准) | 快 | **极快** |
| 生态/插件 | **最强** | 中 | 少(功能受限) |
| 定位 | 全功能可扩展 | 高性能转译器 | 转译/打包一体 |

> 现状:Vite 原生基于 esbuild 做**依赖预构建**,SWC 被 Next.js 等采用;但需要**深度自定义插件**时,Babel 生态仍不可替代。三者常共存:Babel 兜底复杂场景,SWC/esbuild 提速度。

---

## 五、小结

```
转译器 = 语法转换 + polyfill + 能力扩展
Babel:parse → transform(plugin/preset,preset-env 按 target 转)→ generate
polyfill:补 API(core-js + useBuiltIns: usage)
演进:Babel(JS,全功能)→ SWC(Rust)/esbuild(Go,快 10~100 倍)
```

## 六、面试题

**Q1:`preset` 和 `plugin` 的区别?**

`plugin` 是**单个**转换能力(如"转箭头函数");`preset` 是**一组 plugin 的预设集合**(如 `preset-env`、`preset-react`),开箱即用。执行顺序:plugin 先于 preset,且多个 plugin 按声明顺序。

**Q2:语法转译和 polyfill 的区别?**

**语法转译**改的是"语法结构"(箭头函数→function、可选链→判断),把新语法变旧语法;**polyfill** 补的是"运行时 API"(`Promise`、`Object.assign`、`includes` 这些方法是环境缺什么补什么)。两者解决不同层面的兼容。

**Q3:为什么 esbuild 比 Babel 快那么多?**

esbuild 用 **Go** 编译型语言编写、编译到原生机器码,且内部高度并行、复用 AST、少做不必要的抽象;Babel 是 **JavaScript** 实现,跑在 JS 引擎上、插件模型层数多。这是"解释执行 vs 编译执行"的性能差距。
