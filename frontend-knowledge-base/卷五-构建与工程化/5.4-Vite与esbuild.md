# 5.4 Vite 与 esbuild

> 卷:卷五 · 构建与工程化
> 阅读时间:25min

---

## 引言:Vite 为什么"一启动就能开发"

webpack 思路是"先全量打包再启动",越大越慢;Vite 反其道:**开发期不打包**,靠原生 ESM + 按需编译,快得惊人。深挖要懂**双引擎的取舍逻辑**。

---

## 一、双引擎:开发用 esbuild,构建用 Rollup

```mermaid
flowchart TB
    subgraph 开发 dev
    A[native ESM 加载] --> B[请求到哪个模块]
    B --> C[esbuild 瞬编译该模块]
    end
    subgraph 构建 build
    D[全量依赖分析] --> E[Rollup 打包]
    E --> F[产物 树摇 分包]
    end
```

| 阶段 | 引擎 | 为什么 |
|------|------|--------|
| 开发 | esbuild + 原生 ESM | 快,不打包,按需 |
| 构建 | **Rollup** | 树摇好、产物干净 |

**为什么开发用 esbuild、构建用 Rollup(深层)?** 开发求"**最快**"(启动/HMR),esbuild 极快且只需"能跑";构建求"**最优产物**"(极致树摇、分包控制、兼容),Rollup 更成熟稳定。**"开发求速、构建求优"** 的分工。

---

## 二、三个关键机制

### 1. 依赖预构建

`node_modules` 里的库(CJS、海量小文件)按原生 ESM 逐个请求会爆炸。Vite 启动时用 esbuild **预构建**:

- CJS → ESM
- 分散小文件 → 合并成单个(如 `lodash-es` 几百个模块 → 一个)

### 2. 按需编译 + 秒级 HMR

浏览器**请求到哪个文件**,esbuild 才现编译哪个;改哪个文件,**只失效那一条链**,毫秒替换、状态不丢。

### 3. 构建走 Rollup

生产求最优产物,交给 Rollup(5.5),`rollupOptions` 可透传定制。

---

**一个典型的 vite.config.js:**

```js
import { defineConfig } from "vite";
import vue from "@vitejs/plugin-vue";

export default defineConfig({
  plugins: [vue()],                 // 插件
  resolve: { alias: { "@": "/src" } }, // 路径别名
  server: {
    port: 5173,
    proxy: {                        // 开发代理(解决跨域)
      "/api": {
        target: "https://api.example.com",
        changeOrigin: true,
        rewrite: (p) => p.replace(/^\/api/, ""),
      },
    },
  },
  build: {
    outDir: "dist",
    sourcemap: true,
    rollupOptions: { external: ["lodash"] }, // 透传 Rollup(呼应 5.5)
  },
});
```

> 关键:开发期 `server.proxy` 解决跨域(浏览器全程同源,呼应 [4.6](/卷四-网络与通信/4.6-跨域与同源策略));构建期 `build.rollupOptions` 透传 Rollup——Vite 是"esbuild(dev)+ Rollup(build)"的封装。

## 三、Vite vs webpack(选型)

| | Vite | webpack |
|---|------|---------|
| 开发启动 | **秒级** | 秒到分钟 |
| HMR | 极快(按需失效) | 随项目变大 |
| 引擎 | esbuild(dev)+ Rollup(build) | tapable 体系 |
| 生态 | 成长中 | **最全** |

> 新项目默认 Vite;存量复杂项目 webpack;Rolldown 正成 Vite 未来构建内核(5.6)。

## 四、小结

```
Vite 双引擎:dev esbuild(预构建+不打包+按需),build Rollup
三机制:依赖预构建(CJS→ESM,合并)/ 按需编译+秒级 HMR / 构建 Rollup
分工本质:开发求速(esbuild),构建求优(Rollup)
```

## 五、面试题

**Q1:Vite 为什么开发"几乎秒开",webpack 却越来越慢?**

Vite 开发期**不打包**:原生 ESM,请求到哪个模块才用 esbuild 现编译哪个(按需);webpack 要**全量打包**再启动。这是"按需 vs 全量"的差异。

**Q2:Vite 的"依赖预构建"解决什么问题?**

`node_modules` 里的库常是 CJS、拆成海量小文件。预构建用 esbuild 把它们① **CJS→ESM**、② **合并成大模块**,避免浏览器成千上万请求,兼顾"不打包"与"加载效率"。

**Q3:为什么 Vite 开发用 esbuild、构建用 Rollup?**

开发求**最快**(esbuild 极快);构建求**最优产物**(Rollup 树摇/分包更成熟)。"开发求速、构建求优"。

**Q4:Vite 的 HMR 为什么比 webpack 快?**

Vite 的 HMR 是"**按需失效**":只让改动的模块链失效重载,且不打包、只转译单文件;webpack 要重新构建受影响的 chunk。所以 Vite HMR 近乎瞬时、状态不丢。

**Q5:一个 Vite 项目冷启动时,那行"预构建依赖"日志在干什么?**

在启动时用 esbuild 对 `node_modules` 做**预构建**(CJS→ESM、合并小模块),结果缓存起来,让后续按需加载高效。改依赖后会自动重新预构建。

**Q6:Vite 能完全替代 webpack 吗?什么情况仍用 webpack?**

大多数新项目可替代;但**深度定制的复杂存量项目、特殊 loader/插件生态、兼容性要求高**的场景,webpack 生态更全更稳,迁移成本高,仍用 webpack。
