## 引言:依赖这么装,为什么还会"装错"

包管理器决定"装什么、怎么存、怎么解析"。了解 npm → yarn → pnpm 的演进,才能看懂 `node_modules` 里的门道,以及"**幽灵依赖**"这个经典坑。

---

## 一、三大包管理器对比

| | npm | yarn | pnpm |
|---|-----|------|------|
| 安装方式 | 嵌套/flat | flat | **符号链接(硬链接内容寻址)** |
| 速度 | 慢(历史) | 快 | **最快、省磁盘** |
| 磁盘占用 | 大(重复) | 大 | **极小(全局 store 复用)** |
| 严格性 | 松(易出幽灵依赖) | 较松 | **严格**(显式依赖) |
| 缘起 | 默认 | npm 的替代品 | 解决磁盘与"幽灵依赖" |

> 趋势:新项目普遍 **pnpm**,bun 则是"运行时 + 包管理 + 打包"一体的新玩家(见下文)。

## 二、npm 的"幽灵依赖"问题

```mermaid
flowchart TD
    A[你的项目声明依赖 A] --> B[A 依赖了 lodash]
    B --> C[lodash 被提升 hoist 到<br/>node_modules 顶层]
    C --> D[你的代码直接 require('lodash') 也能用]
    D --> E[但你没声明它!]
    E --> F[A 升级移除 lodash → 你的代码突然崩]
```

**幽灵依赖**:你没在 `package.json` 里声明,却因为"依赖提升(hoisting)"而**间接可用**的包。风险:上游一变,你的隐式依赖就断,极其脆弱。

**pnpm 的解法**:用**符号链接**让每个包只能访问**自己声明过**的依赖,幽灵依赖直接不存在:

```
node_modules
├── .pnpm/            ← 真正的包(内容寻址存储)
│   └── lodash@4.17.21/
├── vue -> .pnpm/vue@.../        ← 只有你声明的包才有顶层链接
└── (你没声明 lodash,所以这里根本没有它)
```

## 三、pnpm 的三大特性

1. **硬链接 + 内容寻址存储**:所有项目共享一份全局 store(`~/.pnpm-store`),同样的包只存一份 → 省磁盘
2. **符号链接 node_modules**:只有**显式声明**的依赖可访问 → 治幽灵依赖
3. **workspace 原生支持**:Monorepo 的核心工具(见 5.8)

```bash
npm install -g pnpm
pnpm add vue            # 安装
pnpm add -D typescript  # 开发依赖
pnpm --filter web dev   # 针对 workspace 中某子包执行
```

## 四、bun:运行时 + 包管理 + 打包 一体

Bun 不只是包管理器,而是**用 Zig 写的 JS 运行时**(对标 Node)+ 内置打包/转译:

| 能力 | bun 命令 |
|------|---------|
| 包管理(极快安装) | `bun install` |
| 运行时 | `bun run index.ts`(原生跑 TS!) |
| 打包 | `bun build ./src/index.ts` |
| 测试 | `bun test` |

> bun 生态仍在追赶 Node 的兼容覆盖,但它"安装快、原生 TS、内置打包"对中小工具类项目很香。

## 五、语义化版本与 lockfile

### 1. 版本号规则(Semver)

```
1.2.3 → 主版本(破坏性).次版本(新功能兼容).补丁(修 bug)
```

| 范围 | 含义 | 示例 |
|------|------|------|
| `^1.2.3` | 兼容主版本,可升到 < 2.0.0 | 默认写死主版本 |
| `~1.2.3` | 兼容次版本,只升补丁 | < 1.3.0 |
| `1.2.3` | 精确锁定 | 完全一致 |

### 2. lockfile 的作用

`package-lock.json` / `pnpm-lock.yaml` **锁死实际安装的精确版本**,保证团队/CI 装出来**完全一致**,避免"我机器能跑、你机器崩"。

```bash
# 部署环境务必用能复现 lockfile 的安装
pnpm install --frozen-lockfile
```

## 六、小结

```
包管理演进:npm(历史)→ yarn(提速)→ pnpm(符号链接,治幽灵依赖,省磁盘)
幽灵依赖:没声明却间接可用 → pnpm 用符号链接根治
bun:Zig 写的运行时+包管理+打包一体
版本:^ 锁主版本 / ~ 锁次版本;lockfile 保证可复现
```

## 七、面试题

**Q1:什么是"幽灵依赖"?pnpm 如何解决?**

幽灵依赖 = 你没在 `package.json` 声明、却因 npm 的依赖提升(hoisting)而**间接可用**的包,上游一变动就崩。pnpm 用**符号链接**,每个包只能访问自己**显式声明**的依赖,不提升、无幽灵依赖。

**Q2:pnpm 为什么省磁盘且安装快?**

它用**内容寻址存储**:所有项目共用一份全局 store,相同版本的包在磁盘上**只存一份**,各项目的 `node_modules` 用**硬链接/符号链接**指向它。所以既不重复占空间,安装时也大多是"链接"而非"复制",速度更快。

**Q3:`^` 和 `~` 的区别?lockfile 有什么用?**

`^1.2.3` 允许升级到 `<2.0.0`(锁主版本),`~1.2.3` 只允许补丁升级 `<1.3.0`(锁次版本)。lockfile 锁死**实际解析出的精确版本**,让团队和 CI 安装结果**可复现一致**。
