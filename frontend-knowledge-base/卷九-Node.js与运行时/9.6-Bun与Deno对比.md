# 9.6 Bun / Deno 对比

> 卷:卷九 · Node.js 与运行时
> 难度:⭐ 基础(前沿) | 阅读时间:15min

---

## 引言:JS 运行时不再是 Node 一家

Deno(Node 作者的"第二版")、Bun(性能怪兽)都来了。这一章给三者画像 + 选型建议,避免只会 Node。

---

## 一、三者速览

| | Node.js | Deno | Bun |
|---|---------|------|-----|
| 引擎 | V8 | V8 | **JavaScriptCore**(更快) |
| 语言 | JS | **原生 TS** | 原生 TS |
| 包管理 | npm(需外部) | 内置 + URL 导入 | **内置,极快** |
| 安全 | 无默认沙箱 | **默认权限沙箱** | 无默认沙箱 |
| 速度 | 基准 | 中 | **最快**(安装/运行) |
| 生态 | **最大最成熟** | 小 | 增长中 |

---

## 二、Deno:安全的现代重构

```js
// 原生跑 TS,默认沙箱,访问网络/文件需显式授权
deno run --allow-net --allow-read server.ts
```

- **安全模型**:默认无网络/文件/环境权限,`--allow-*` 显式授予(治"npm 投毒")
- **内置工具**:格式化、lint、测试、打包一把梭,无 `node_modules`(URL 导入)

---

## 三、Bun:性能 + 一体化

```bash
bun install          # 极快安装
bun run index.ts     # 原生跑 TS
bun build ./src/index.ts  # 内置打包
bun test             # 内置测试
```

- **性能**:JavaScriptCore 引擎,启动与运行都快
- **一体化**:运行时 + 包管理 + 打包 + 测试,省一堆工具链
- 兼容目标:尽量对齐 Node API,但生态覆盖仍在追

---

## 四、选型建议(务实)

| 场景 | 建议 |
|------|------|
| 生产后端、生态/兼容优先 | **Node**(最稳) |
| 边缘函数/Serverless 冷启动 | Bun / Deno(启动快) |
| 个人工具、CLI、脚本 | Bun(开箱即用、快) |
| 重视安全/想绕开 npm 生态 | Deno |

> 核心原则:**生产看生态与稳定(选了 Node),个人工具看体验(可试 Bun/Deno)**。它们都在向"兼容 Node"靠拢,未来差距会更小。

---

## 小结

```
Node:V8 + npm 生态最大,生产首选
Deno:V8 + 原生 TS + 默认权限沙箱(安全)
Bun:JavaScriptCore + 一体化 + 最快

选型:生产稳 → Node;冷启动/工具/脚本 → Bun;安全优先 → Deno
```

## 面试题

**Q1:Deno 和 Node 的核心区别?**

① Deno 由 Node 原作者打造,解决了 Node 历史包袱;② **原生支持 TS**、无 `node_modules`(URL 导入);③ **默认安全沙箱**(访问网络/文件需 `--allow-*` 授权,Node 无此默认);④ 内置 lint/format/test/task 工具链。

**Q2:Bun 为什么快?**

它用 **JavaScriptCore**(苹果引擎,启动与执行都快)替代 V8,且用 **Zig** 编写运行时/包管理,`bun install` 并行下载、硬链接复用;同时**内置打包/测试**,减少工具链开销。性能是其主打。

**Q3:生产环境你会选 Node 还是 Bun?为什么?**

倾向 **Node**:生态最成熟、兼容性稳定、大厂生产验证充分、排查资料多。Bun/Deno 虽有性能与体验优势,但生态与边界场景覆盖仍不完整,适合**工具/脚本/新项目试水**,而非关键后端首选。
