# 9.6 Bun / Deno 对比

> 卷:卷九 · Node.js 与运行时
> 阅读时间:15min

---

## 引言:JS 运行时不再是 Node 一家

Deno(Node 作者"第二版")、Bun(性能怪兽)都来了。深挖要懂 Deno 的**默认沙箱**与 Bun 快的**引擎原因**。

---

## 一、三者速览

| | Node | Deno | Bun |
|---|------|------|-----|
| 引擎 | V8 | V8 | **JavaScriptCore** |
| 语言 | JS | **原生 TS** | 原生 TS |
| 包管理 | npm | 内置 + URL 导入 | **内置极快** |
| 安全 | 无默认沙箱 | **默认权限沙箱** | 无 |
| 速度 | 基准 | 中 | **最快** |

---

## 二、Deno:安全现代重构(底层)

```js
deno run --allow-net --allow-read server.ts   // 显式授权
```

**默认沙箱**:默认无网络/文件/环境权限,`--allow-*` 显式授予——治"npm 投毒"(依赖包默认不得访问敏感资源)。内置 lint/format/test/task,无 `node_modules`(URL 导入)。

---

## 三、Bun:性能 + 一体化(底层)

```bash
bun install; bun run index.ts; bun build; bun test
```

**为什么 Bun 快?** 用 **JavaScriptCore**(苹果引擎,启动/执行都快)替代 V8;用 **Zig** 写运行时/包管理;`bun install` 并行下载 + 硬链接复用。

---

## 四、选型建议(务实)

| 场景 | 建议 |
|------|------|
| 生产后端、生态/兼容优先 | **Node**(最稳) |
| 边缘/Serverless 冷启动 | Bun / Deno |
| 个人工具、CLI、脚本 | Bun(开箱即用快) |
| 重视安全/绕开 npm | Deno |

> 原则:**生产看生态与稳定(Node),个人工具看体验(Bun/Deno)**。都在向 Node 兼容靠拢。

---

## 五、小结

```
Node:V8 + npm 生态最大,生产首选
Deno:V8 + 原生 TS + 默认沙箱(安全)
Bun:JavaScriptCore + 一体化 + 最快
选型:生产稳→Node;冷启动/工具→Bun;安全→Deno
```

---

## 六、面试题

**Q1:Deno 和 Node 的核心区别?**

① Node 作者重写,解决历史包袱;② **原生 TS**、无 node_modules(URL 导入);③ **默认安全沙箱**(--allow-* 授权);④ 内置 lint/format/test 工具链。

**Q2:Bun 为什么快?**

用 **JavaScriptCore**(启动/执行快)+ **Zig** 写运行时,`bun install` 并行下载 + 硬链接;内置打包/测试减少工具链开销。

**Q3:生产环境选 Node 还是 Bun?为什么?**

倾向 **Node**:生态最成熟、兼容稳定、生产验证充分。Bun/Deno 有性能/体验优势,但生态与边界覆盖仍不完整,适合工具/脚本/试水,非关键后端首选。

**Q4:Deno 的"默认沙箱"解决什么问题?**

默认不给网络/文件/环境权限,**依赖包默认无法访问敏感资源**,从根上缓解"npm 包投毒/供应链攻击";需权限时显式 `--allow-*`。

**Q5:"原生 TS"意味着什么?Node 呢?**

Deno/Bun **直接执行 TS**,无需转译工具链;Node 原生只跑 JS,TS 需 ts-node/tsx 或先编译。前者开发体验更顺。

**Q6:Bun 能否完全替代 Node for 生产?**

目前**不能完全替代**:生态兼容(某些 Node 原生模块/边界行为)仍在追赶,生产验证与排查资料不如 Node。适合工具/新项目,关键后端仍 Node 为主。
