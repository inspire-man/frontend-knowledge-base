# 9.6 Bun / Deno 对比

## 引言:JS 运行时不再是 Node 一家

Deno(Node 作者"第二版")、Bun(性能怪兽)都来了。深挖要懂 Deno 的**默认沙箱**、Bun 快的**引擎原因**、以及三者共同遵循的 **Web 标准 API**。

---

## 一、共同趋势:Web 标准 API

三者越来越往**同一套 Web 标准 API**靠拢——`fetch`、`Request`/`Response`、`WebSocket`、`Streams`、`AbortController` 现在都是运行时内置,不再需要 `node-fetch` 之类的 polyfill。

```js
// 三运行时都原生支持(无需 npm 包)
const res = await fetch("https://api.example.com");
const data = await res.json();
```

> 意义:代码**跨运行时可移植**。你写的 `fetch` 在 Node/Deno/Bun/浏览器/边缘函数都能跑。

---

## 二、三者速览

| | Node | Deno | Bun |
|---|------|------|-----|
| 引擎 | V8 | V8 | **JavaScriptCore** |
| 语言 | JS(TS 需转译) | **原生 TS** | **原生 TS** |
| 包管理 | npm | 内置 + URL 导入 + npm 兼容 | **内置极快** |
| 安全 | 无默认沙箱 | **默认权限沙箱** | 无 |
| npm 兼容 | 原生 | 2.x 起兼容 `npm:` | 大部分兼容 |
| 冷启动 | 较慢 | 快 | **最快** |
| 工具链 | 需拼装 | **内置 lint/format/test** | **内置 bundler/test** |

---

## 三、Deno:安全现代重构

### 3.1 默认沙箱(核心差异)

```bash
deno run --allow-net --allow-read server.ts   # 显式授权网络/文件
deno run server.ts                            # 默认无任何权限
```

**默认沙箱**:默认无网络/文件/环境/FFI 权限,必须 `--allow-*` 显式授予。意义:治"npm 投毒/供应链攻击"——依赖包默认**无法访问敏感资源**。

### 3.2 内置工具链(开箱即用)

```bash
deno fmt            # 格式化(内置 prettier 类似能力)
deno lint           # lint
deno test           # 测试
deno compile main.ts   # 编译成单文件可执行(无依赖分发!)
deno bundle         # 打包
```

配置走 `deno.json`:

```json
{
  "tasks": { "dev": "deno run --watch main.ts" },
  "imports": { "lodash": "npm:lodash@4" },
  "fmt": { "singleQuote": true }
}
```

### 3.3 模块:URL 导入 vs npm

```js
// URL 导入(早期 Deno 特色,无 node_modules)
import { serve } from "https://deno.land/std/http/server.ts";

// Deno 2.x 也兼容 npm 包
import _ from "npm:lodash@4";
```

> Deno 早期坚持 URL 导入、无 `node_modules`;Deno 2.x 起**回补了 npm 兼容**(`npm:` 前缀),降低迁移门槛。

---

## 四、Bun:性能 + 一体化

### 4.1 为什么快(引擎层)

1. **JavaScriptCore**(苹果 Safari 引擎)替代 V8:启动、执行都快,尤其冷启动
2. 运行时、包管理器用 **Zig** 编写(高性能、无 GC 的系统语言)
3. `bun install` **并行下载 + 硬链接复用**,速度远超 npm/yarn/pnpm

```bash
bun install; bun run index.ts; bun build; bun test
```

### 4.2 内置 API(一体化优势)

```js
// bun.serve:内置 HTTP 服务器(免 express)
Bun.serve({
  port: 3000,
  fetch(req) { return new Response("Hello"); },
});

// bun:sqlite:内置 SQLite(免安装驱动)
import { Database } from "bun:sqlite";
const db = new Database("app.db");
db.query("CREATE TABLE IF NOT EXISTS t (id INTEGER)").run();
```

### 4.3 与 Node 的兼容

Bun 目标**兼容大部分 Node API**(`fs`/`path`/`http`/`crypto` 等可直接用),但仍有些 Node 原生模块/边界行为未完全覆盖——这是它"还不能完全替代 Node 生产"的主因。

---

## 五、选型建议(务实)

| 场景 | 建议 | 理由 |
|------|------|------|
| 生产后端、生态/兼容优先 | **Node** | 最稳、生态最大、验证充分 |
| 边缘/Serverless 冷启动敏感 | Bun / Deno | 冷启动快 |
| 个人工具、CLI、脚本 | **Bun** | 开箱即用、快 |
| 重视安全/供应链 | **Deno** | 默认沙箱 |
| 单文件可执行分发 | Deno | `deno compile` |

> 原则:**生产看生态与稳定(Node),工具看体验(Bun/Deno)**。三者都在向 Node 兼容靠拢。

---

## 六、小结

```
共同:Web 标准 API(fetch/Streams/WebSocket)三运行时共享,代码可移植
Node:V8 + npm 生态最大,生产首选
Deno:V8 + 原生 TS + 默认沙箱(安全)+ 内置工具链 + deno compile
Bun:JavaScriptCore + Zig + 一体化(bun.serve/bun:sqlite)+ 最快冷启动
选型:生产稳→Node;冷启动/工具→Bun;安全→Deno
```

## 七、面试题

**Q1:Deno 和 Node 的核心区别?**

① Node 作者重写,解决历史包袱;② **原生 TS**、早期无 node_modules(URL 导入,2.x 起兼容 npm);③ **默认安全沙箱**(--allow-* 授权);④ 内置 lint/format/test/compile 工具链。

**Q2:Bun 为什么快?**

用 **JavaScriptCore**(启动/执行快,尤其冷启动)+ **Zig** 写运行时与包管理;`bun install` 并行下载 + 硬链接复用;内置 bundler/test 减少工具链开销。

**Q3:生产环境选 Node 还是 Bun?为什么?**

倾向 **Node**:生态最成熟、兼容稳定、生产验证充分。Bun/Deno 有性能/体验优势,但生态与边界覆盖仍不完整,适合工具/脚本/试水,关键后端仍 Node 为主。

**Q4:Deno 的"默认沙箱"解决什么问题?**

默认不给网络/文件/环境权限,**依赖包默认无法访问敏感资源**,从根上缓解"npm 包投毒/供应链攻击";需权限时显式 `--allow-*`。

**Q5:"原生 TS"意味着什么?Node 呢?**

Deno/Bun **直接执行 TS**,无需转译工具链;Node 原生只跑 JS,TS 需 ts-node/tsx 或先编译(注:Node 22+ 已有实验性 strip types,但仍需关注)。前者开发体验更顺。

**Q6:Bun 能否完全替代 Node for 生产?**

目前**不能完全替代**:生态兼容(某些 Node 原生模块/边界行为)仍在追赶,生产验证与排查资料不如 Node。适合工具/新项目,关键后端仍 Node 为主。

**Q7:三者共同遵循的"Web 标准 API"有什么意义?**

`fetch`/`Request`/`Response`/`WebSocket`/`Streams` 成为运行时内置,代码**跨运行时可移植**(Node/Deno/Bun/浏览器/边缘都能跑),不再依赖 `node-fetch` 等 polyfill。

**Q8:`deno compile` 有什么独特价值?**

把 TS 应用编译成**单文件可执行文件**(内置运行时),目标机器无需装 Deno 也能跑——适合 CLI 工具、内部脚本分发,类似 Go 的"单二进制"体验。
