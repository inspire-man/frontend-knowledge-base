# 9.4 包与发布(npm publish / npm link / 版本)

## 引言:把自己的代码"包装、发布、给别人用"

这是组件库/CLI 工具作者的基本功。深挖要懂 **`exports` 字段的条件分发**、**semver 版本规则**与 `files` 的发布控制。

---

## 一、package.json 核心字段

```json
{
  "name": "my-utils",
  "version": "1.0.0",
  "main": "dist/index.js",
  "module": "dist/index.esm.js",
  "exports": { ".": { "import": "./dist/esm.js", "require": "./dist/cjs.js" } },
  "types": "dist/index.d.ts",
  "files": ["dist"],
  "scripts": { "build": "rollup -c" }
}
```

| 字段 | 作用 |
|------|------|
| `main` | CJS 入口 |
| `module` | 打包工具的 ESM 入口 |
| `exports` | **现代分发入口**(优先级高于 main/module) |
| `types` | TS 类型声明入口 |
| `files` | 白名单:只发布这些文件 |

### exports 的条件分发(底层)

同一包按加载方式分发不同产物:

```json
"exports": {
  ".": {
    "import": "./dist/esm.js",   // import 拿 ESM(可树摇)
    "require": "./dist/cjs.js",  // require 拿 CJS
    "types": "./dist/index.d.ts",
    "default": "./dist/cjs.js"   // 兜底
  },
  "./feature": "./dist/feature.js"   // 额外暴露子路径
}
```

> 两个关键点:① `exports` 一旦定义,**会限制子路径访问**(没列出的子路径 `my-utils/src/xxx` 会被挡);② 条件按**对象键顺序**匹配,`types` 建议放最前(TS 优先读类型)。这是"库同时支持 ESM/CJS"的标准做法(呼应 [5.5](/卷五-构建与工程化/5.5-Rollup深入))。

## 二、semver 版本规范

```
1 . 2 . 3
主 . 次 . 补丁
```

| 段 | bump 时机 | 例子 |
|----|----------|------|
| 主 major | **破坏性** API 变更 | 1.2.3 → 2.0.0 |
| 次 minor | 向后兼容**新功能** | 1.2.3 → 1.3.0 |
| 补丁 patch | **bug 修复** | 1.2.3 → 1.2.4 |

### 版本范围符(依赖声明里的 ^ ~)

```json
{ "dependencies": { "lodash": "^4.17.0", "react": "~18.2.0" } }
```

| 符号 | 含义 |
|------|------|
| `^4.17.0` | 允许 minor/patch 更新(4.x 内,≥4.17.0) |
| `~18.2.0` | 只允许 patch 更新(18.2.x 内) |
| `*` / `latest` | 最新 |
| 精确 `1.2.3` | 锁定该版本 |

### 预发布与 dist-tag

```
1.0.0-beta.1 / 1.0.0-rc.2      # 预发布版本
npm publish --tag beta          # 发到 beta 标签(默认 latest)
npm install my-utils@beta       # 装 beta 标签的版本
```

## 三、npm publish 流程 + checklist

```bash
npm login
npm version patch     # bump 版本 + 打 git tag
npm pack --dry-run    # 预览"将要发布哪些文件"(重要!)
npm publish
```

**发布前 checklist:**

1. `files` 精简(只发 dist + README + package.json)
2. 去 `private: true`(否则拒发)
3. 版本符合 semver 且没发过(重号会报错)
4. `.npmignore` 排除源码/sourcemap
5. `npm pack --dry-run` 预览,确认没漏/没多

## 四、npm link:本地调试

```bash
# 库目录
npm link                 # 链接到全局
# 消费方项目
npm link my-utils        # 软链接进 node_modules → 改库即时生效
```

> 原理:**软链接指向库源码目录**,改库代码消费方立刻看到(免反复 publish)。替代:monorepo 的 `workspace:*`(5.8)。

## 五、scope 与私有源

```json
{ "name": "@myorg/utils" }        // scoped 包(带组织前缀)
```

```bash
npm config set registry https://registry.npmmirror.com   # 换源
npm publish --registry https://npm.myorg.com/            # 发私有源
npm login --registry https://npm.myorg.com/              # 私有源登录
```

> scoped 包默认是**私有**的,发布要 `--access public` 或走付费私有;换源解决国内 npmjs 慢的问题。

## 六、小结

```
核心字段:main/module/exports(条件分发,会限制子路径)+ types + files
semver:主.次.补丁;^允许minor/patch,~只patch;dist-tag管理预发布
publish:login → version(打tag)→ pack --dry-run 预览 → publish
npm link:软链接本地联调;scope/私有源按组织管理
```

## 七、面试题

**Q1:exports 字段的 import/require 条件有什么作用?**

让同一包**按加载方式分发不同产物**:import 拿 ESM(可树摇),require 拿 CJS。是"库同时支持 ESM/CJS"的标准做法。

**Q2:如何让 IDE 和 TS 正确识别你发布的包?**

包里加 `types` 字段指向 `dist/index.d.ts`,让 TS 拿到类型提示;否则使用方是隐式 any 或需 @types。

**Q3:npm link 的原理?何时用?**

软链接:全局 + 消费方 node_modules 都指向**库源码目录**,改库代码即时生效(免反复 publish)。用于"开发库的同时在项目里试用"。

**Q4:npm version patch 做了什么?**

按 semver bump 版本号(patch: 1.0.0→1.0.1)+ **打一个 git tag**,供版本追溯与发布。

**Q5:为什么发布要控制 `files` 字段?**

只发布**必要产物**(dist、README),排除源码/测试/sourcemap,减小包体积、避免泄露内部实现。

**Q6:semver 里 `1.2.3` 三段分别代表什么?何时 bump 哪个?**

`主.次.补丁`。**主**:破坏性 API 变更;**次**:向后兼容新功能;**补丁**:bug 修复。发布时按变更性质 bump 相应段。

**Q7:exports 定义后,使用方还能 `require('my-utils/src/内部文件')` 吗?**

不能。`exports` 一旦定义就会**限制子路径访问**,未列出的子路径会被挡(抛 ERR_PACKAGE_PATH_NOT_EXPORTED)。要暴露就显式加 `"./src/*": "./dist/*"` 之类的映射。

**Q8:`^1.2.3` 和 `~1.2.3` 依赖声明有什么区别?**

`^1.2.3` 允许 **minor 和 patch** 更新(1.x 内,≥1.2.3);`~1.2.3` 只允许 **patch** 更新(1.2.x 内)。`^` 更宽松、更常见;`~` 更保守。
